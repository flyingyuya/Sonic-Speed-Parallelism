# 技能包（Skills）

本目录下的技能包是**从本工程的实际失败中提炼出来的方法论**，而不是通用的教程。
每一份都遵循同一套结构：触发条件 → 方法 → 可核验的判据 → 适用边界。
它们的作用是把「踩过的坑」变成「下次不会再踩的规则」。

## 三级知识沉淀

本工程的开发经验分三级存放，颗粒度由细到粗：

| 层级 | 位置 | 规模 | 特点 |
|---|---|---|---|
| **问题账本** | [`docs/08-skills-index.md`](../../docs/08-skills-index.md) | **825 条** | 原始记录：现象 / 根因 / 修复 / 量化改善。可检索，不抽象 |
| **技能包** | `.pi/skills/`（本目录） | **3 个** | 从账本聚类抽象出的方法：触发条件 / 方法 / 判据 / 边界 |
| **状态快照** | [`docs/14-status-snapshot.md`](../../docs/14-status-snapshot.md) | 1 份 | 当前能用的 / 已知受限的 / 待办的 |

**沉淀流程**：观察（账本条目）→ 追问根因 → 聚类成通类 → 抽象成规则 → 写成可执行判据 → 补上适用边界。

## 三个技能包

### 1. `fixed-point-dsp` —— 定点 DSP 的精度预算

**解决什么**：在 FPGA 上实现 IIR / FIR / FFT 时，如何选 Q 格式与位宽、
如何做舍入与饱和、如何验证精度真的够用。

**来自哪些失败**：
- EQ 频响与理论值差 **3 dB**（位宽不足）
- 「参数改大反而变小」（`WAVE_AMP=80` 的低 6 位被静默截断成 16）
- 某个频点发散（二阶低架在近直流处的条件数极差）

**验证有效**：用该包的流程重做 EQ，频响误差从 3 dB 降到 **0.5 dB**；
截断类问题在后续 6 个位宽参数上**零复发**。

**边界**：适用定点 IIR / FIR / FFT，数据位宽 16~32 bit，DSP48 可用。
不适用浮点算法，也不适用位宽低于 12 bit 的极低功耗场景
（那种情况应该换结构，而不是继续调位宽）。

**参考文件**：
- `references/q-format-and-rounding.md` —— Q 格式选择与舍入/饱和实现
- `references/biquad-structure-choice.md` —— 一阶 vs 二阶、级联顺序与条件数

### 2. `fpga-rtl-flow` —— 纯 RTL 工程的无 GUI 流程

**解决什么**：不打开 Vivado GUI，如何完成「仿真 → 综合 → 实现 → 上板」
全流程，以及如何从构建报告里快速定位问题。

**来自哪些失败**：
- `command not found`（工具链路径不明）
- DRC 报组合环但 GUI 不报（工程模式与非工程模式行为不同）
- 时序违例查错方向（应先查约束，再查逻辑）
- `place_design` 失败被误当成「综合错误」
- 完整构建要 9 分 38 秒，迭代太慢

**验证有效**：构建时间 **9m38s → 2m57s**（`SYNTH_ONLY` 模式）；
仿真回归 **20m54s → 1m30s**（并行 + 默认跳过整机冒烟）；
后续 20 多次构建**零次**因「找错报告」而返工。

**边界**：适用纯 RTL、无 block design 的工程（Vivado 2019+ / Quartus 18+）。
不适用含 IP integrator 的工程（`.bd` 文件无法手工编辑），
也不适用需要部分重配置的场景。

**参考文件**：
- `references/vivado-batch-cheatsheet.md` —— batch 模式命令与报告挖掘顺序
- `references/mmcm-clocking.md` —— MMCM 参数计算与时钟约束

### 3. `rtl-verification` —— RTL 自动化验证

**解决什么**：如何建立一套「改完就能立刻知道对不对」的验证体系，
包括黄金模型、激励设计、协议行为模型，以及 testbench 自身的时序陷阱。

**来自哪些失败**：
- TB 在**信号自己更新的沿**上读它（`negedge sd_clk == posedge div_clk`，总差一拍）
- 非阻塞赋值在同一 `always` 里读不到新值
- 跨帧状态和帧内状态共用了一个复位（重配时永久卡死）
- 只测了「第一次触发」，没测「第二次」，漏掉了整条重配路径

**验证有效**：39 个 testbench 中**至少 12 个在第一次跑就红**。
虽然问题账本里大部分失败是仿真发现不了的（要靠综合报告、资源报告、上板），
但仿真抓到的那十几条，每一条都对应上板时会花掉一两天的 bug。

**边界**：适用确定性数字逻辑。不适用模拟/混合信号，
也不适用于需要形式化证明的协议一致性（本工程用穷举替代）。

**参考文件**：
- `references/golden-model-method.md` —— Python 定点黄金模型与逐位对拍
- `references/debug-playbook.md` —— 调试顺序与常见陷阱清单

## 怎么用

这些文件是 AI 编码代理的技能定义（带 YAML frontmatter 的 Markdown），
由代理在匹配到 `description` 描述的场景时自动加载。人工阅读时，
直接看 `SKILL.md` 正文即可，`references/` 是展开的细节。

**如果你在接手这个工程**，建议的阅读顺序是：

1. 先看 [`docs/14-status-snapshot.md`](../../docs/14-status-snapshot.md) —— 现在能用什么、什么不能用
2. 再看 [`README.md`](../../README.md) 的「复现步骤」 —— 怎么跑起来
3. 要改代码时，按任务类型查对应的技能包

## 关于边界

每个技能包的末尾都写了「适用 / 不适用」。这不是形式上的免责声明，
而是从**真实踩错**的经历里总结出来的。举一个反面例子：

> **不要写**：「BRAM 一定要加 `(* ram_style = "block" *)`」。
>
> 实测表明这条属性在「1 写 2 读跨时钟」的访问模式下**无效**，
> 综合器仍会退化成分布式 RAM，触发 `DRC UTLZ-1`。
>
> **应该写**：「BRAM 推断由**访问模式**决定，属性只是建议。
> 1W1R 可靠；1W2R 跨时钟必退化成 LUTRAM，属性也救不了。」

**把特例当通例，比不知道更危险。**
