\section*{摘\quad 要}
\addcontentsline{toc}{section}{摘要}

本作品在 Xilinx Artix-7 XC7A100T 上以\textbf{纯 RTL}（不使用 HLS、软核或任何现成 IP，
连 TMDS 编码与 5:1 串行化也由原语手写）实现了一套音频一体化系统，覆盖
“采集 $\rightarrow$ 均衡 $\rightarrow$ 频谱分析 $\rightarrow$ 可视化 $\rightarrow$ 交互”
的完整闭环。

系统以 WM8960 编解码器为音频前端（48\,kHz / 24\,bit），采样数据同时进入两条并行流水线：
一是\textbf{5 段定点 IIR 参量均衡器}，逐段做 Q 格式与位宽预算，各段增益可在线独立调节并
实时回放；二是\textbf{1024 点基 2 FFT 频谱分析引擎}，仅用\textbf{一个}蝶形单元配合双口
BRAM 时分复用，硬件开销不到全并行方案的 1/512，整帧处理仅占帧周期的 1.3\%。
频谱结果经对数频率分箱、峰值保持与线性衰减后驱动\textbf{双路独立显示}：
LCD 480$\times$272 作交互界面（8 按钮面板 + 8 行状态栏），
HDMI 640$\times$360 作展示大屏（80 根独立柱 + 波形），
并从 SD 卡读取图片作为动态背景（LCD 1:1 满屏、HDMI 裁中心 320$\times$180 后 2 倍整数放大）。

系统横跨四个时钟域，以格雷码异步 FIFO 与电平翻转握手完成跨域传递。
所有参数可经板载按键或 UART ASCII 命令在一个时钟周期内生效。

整机占用 11\,716 LUT（18.48\%）、100.5 BRAM、26 DSP48，时序全部收敛
（\texttt{clk\_sys} +1.779\,ns / \texttt{clk\_hdmi} +4.028\,ns），
\textbf{综合与实现 0 错误 0 警告}，39 个测试平台全部与 Python 定点黄金模型逐位对拍通过，
并已通过 QSPI Flash 固化实现掉电自启动。

\textbf{关键词}：FPGA；纯 RTL；定点 DSP；频谱可视化；HDMI；跨时钟域

\subsection{选题背景与实际问题}
%-----------------------------------------------------------------------------

音频可视化设备在消费市场需求广泛，例如车载音响频谱显示、直播/演出调音台可视化、Hi-Fi 播放器界面等等。此外，在工业检测领域：
如机械振动频谱监测、电机异响诊断、齿轮箱故障早期预警等案例中也经常依赖于频谱分析方法。虽然目前音频可视化技术已经非常成熟，但现有产品存在一个普遍的结构性矛盾，如\cref{tab:bg}~所示 ：

在功能清单之上，本作品有三个值得单独展开的设计选择，也体现了在实际工程中容易遇到的一些问题以及解决的方法：

\subsubsection*{（一）扫描式双路渲染：一份核心，两块屏}

常规做法是先渲染到帧缓冲，再由扫描逻辑读出，但 640$\times$360$\times$16\,bit 的帧缓冲需要 103 块 BRAM，加上其它模块更是直接达到了 98\% 左右，而本器件只有 135 块，实测会导致布线拥塞、时序更是崩到 $-1.09$\,ns、导致 \texttt{place\_design} 构建失败。

本作品把渲染核心抽象为纯组合函数 $(x, y, \text{mode}) \rightarrow$ \,RGB：

\begin{lstlisting}[language=Verilog, basicstyle=\ttfamily\zihao{6},
                   frame=single, rulecolor=\color{boxFrame}]
// 同一个模块，靠参数决定分辨率和是否画 UI
disp_top #(.HDISP(480), .VDISP(272), .WITH_UI(1)) u_disp_lcd  (...);  // 12.5 MHz
disp_top #(.HDISP(640), .VDISP(360), .WITH_UI(0)) u_disp_hdmi (...);  // 25 MHz
\end{lstlisting}

这样带来的好处主要有三重：1. LCD 侧零 framebuffer，只有 SD 图片需要存储；
2. 换分辨率只改参数，不改逻辑；3. 两路的配色、柱高、波形天然一致，因为它们看的是同一份输入数据。

\subsubsection*{（二）数据柱数与显示柱数解耦}

LCD 的像素宽为 480，使用 60 根柱则每柱 8 像素，可以整除；而 HDMI 的像素宽为 640，若也用 60 根柱则每柱 10.67 像素，无法整除，所以必须用乘法器，但是乘法器会恶化时序。

本作品把数据大小和显示柱数拆成两个独立参数（\texttt{NBARS} / \texttt{NBARS\_DISP}），HDMI 侧改用 80 根柱可以整除，只需移位。更关键的是原本路径由 \texttt{generate} 的恒等分支保护：

\begin{lstlisting}[language=Verilog, basicstyle=\ttfamily\zihao{6},
                   frame=single, rulecolor=\color{boxFrame}]
generate
    if (NBARS_DISP == NBARS) begin : g_ident
        assign bbar = dbar[AW-1:0];              // 综合器看不到除法
    end else begin : g_scale
        assign bbar = (dbar * NBARS) / NBARS_DISP;
    end
endgenerate
\end{lstlisting}

\subsubsection*{（三）三个细节层面的设计}

\begin{itemize}
\item \textbf{静音改用“送 0 数据”而不是“停 I2S”}：\texttt{data\_en} 照常拉高，只是把左右声道数据清零。这样 WM8960 收到的是“合法的 0 采样数据”，链路不会以为对端掉线，避免由静音或取消静音而产生的瞬间爆音。
\item \textbf{跨域握手用“电平翻转”而不是“单拍脉冲”}：\texttt{start} 若是单拍脉冲，跨到更慢的时钟域时可能被整个漏掉；改成翻转一个电平再双打取边沿，无论两侧时钟比多大都不会丢。
\item \textbf{按键活动标志也用电平翻转}：面板的空闲自动收起计时器需要知道“用户刚才是否有动作”，同样不能用一个拍宽的脉冲跨域。
\end{itemize}

\subsection{主要技术特点及创新点}
%-----------------------------------------------------------------------------

\subsubsection*{1. 单蝶形 FFT 的极低资源占用}

1024 点 FFT 若全并行需 512 个蝶形 $\times$ 4 乘法器 $=$ \textbf{2048 个 DSP48}，超出器件总量（240 个）近 8 倍。而本作品用一个蝶形单元加双口 BRAM 进行时分复用：

\begin{table}[H]
\centering
\caption{FFT 架构方案对比（1024 点，48\,kHz 采样）}
\label{tab:fft}
\begin{tabular}{lccccc}
\toprule[1.5pt]
\rowcolor{gray!25} 方案 & 蝶形单元 & DSP48 & BRAM & 整帧耗时 & 占帧周期 \\
\midrule[1pt]
全并行 & 512 & 2048 & 0 & 1 拍 & 0.04\% \\
4 路并行 & 128 & 512 & 0 & 7\,680 拍 & 0.3\% \\
\textbf{单蝶形（采用）} & \textbf{1} & \textbf{4} & \textbf{2} & \textbf{30\,720 拍} & \textbf{1.3\%} \\
\bottomrule[1.5pt]
\end{tabular}
\end{table}

WM8960 采样数据一帧周期大约为 46.9\,ms，而 FFT 计算整帧耗时 $30\,720 \times 20.83\,\text{ns} = 0.64$\,ms，仅占 1.3\%，余量为 75 倍。

\subsubsection*{2. 扫描式渲染，无帧缓冲}

把渲染核心抽象为纯组合函数 $(x,y,\text{mode}) \rightarrow$\,RGB，扫描到哪个像素就算哪个像素。LCD 侧无需任何 framebuffer，一帧 130\,560 个像素全部实时算出。

\subsubsection*{3. 零成本的裁剪与放大}

HDMI 侧需要从 480$\times$272 的全图中裁出中心 320$\times$180 的区域，再放大 2 倍铺满 640$\times$360。在实际操作中，可以通过两次移位相加从而避免使用到乘法器：

\begin{lstlisting}[language=Verilog, basicstyle=\ttfamily\zihao{6},
                   frame=single, rulecolor=\color{boxFrame}]
// 裁剪地址：dy*320 = dy*256 + dy*64 -> 两次移位相加，零 DSP
wire [18:0] crop_addr = (dy << 8) + (dy << 6) + dx;

// 2 倍放大：显示坐标右移 1 位 -> 一个移位，零算术
wire [XW-1:0] fb_sx = (fb_lx >> 1) + FB_CX[XW-1:0];
wire [YW-1:0] fb_sy = (fb_ly >> 1) + FB_CY[YW-1:0];
\end{lstlisting}

\subsubsection*{4. 不同尺寸双帧缓冲替代“双读口”}

两个显示器时钟不同（12.5\,MHz / 25\,MHz）。实测表明 Vivado 的 BRAM 推断不支持“1 写 2 读跨时钟”，会静默退化成分布式 RAM（LUTRAM），触发 \texttt{DRC UTLZ-1} 错误（需 86\,452 个 \texttt{RAMD64E}，仅 19\,000 个可用），加 \texttt{(* ram\_style = "block" *)} 进行约束也无效。

因此本作品改为两份不同尺寸的缓冲，即 LCD 侧直接读取 480$\times$272 的全部图像数据，HDMI 读取对应的 320$\times$180 范围内的裁剪区图像数据后进行 2 倍整数放大，这样一来 BRAM 从 116 块降到 84 块，节省一定资源的同时也避开了由静默推断而导致的错误。

\subsection{设计流程}

本作品采用的不是"写完代码再补测试"的传统流程，而是\textbf{模型先行、逐位对拍、
每轮全量回归}的闭环流程。这样做是因为 RTL 调试的最大成本不在"写"、
而在"怎么确认它是对的"——尤其是定点算法，肉眼根本看不出 1 LSB 的偏差。

整个流程分为\textbf{五条并行推进的线索}，如图~\ref{fig:flow} 所示：

\begin{enumerate}
\item \textbf{规格与判据先行}：在写任何 RTL 之前，先把"怎样算对"写成可执行的判据。
      例如"SD 卡初始化的第一次 \texttt{Go} 必须走完 5 步、\textbf{第二次 \texttt{Go}
      也必须能重新走完}"——这条判据后来救了大命（见第四部分 E 系列案例）。
\item \textbf{黄金模型先行}：每个定点模块先用 Python（\texttt{numpy} / \texttt{mpmath}）
      写出"数学上正确"的参考实现，再做定点量化与误差评估，
      确认位宽够用后，才由脚本生成 RTL 需要的系数表 / 旋转因子表 / 字模。
\item \textbf{RTL 与 Testbench 同步编写}：写一个模块、配一个 testbench，
      两者一起提交。testbench 的判据直接取自第 1 步；
      激励采用"三段式"（复位段 / 正常段 / 边界段），
      边界段必须覆盖"第二次触发"这类容易漏的路径。
\item \textbf{每轮全量回归}：改完任何一个文件，都跑一次 39 个 testbench 的并行回归
      （约 1 分 30 秒），而不是"只跑相关的那几个"。
      曾经因为只跑相关 TB，漏掉了一个跨域信号的 \texttt{UNDRIVEN}，
      直到上板才发现。
\item \textbf{综合报告是第二道关}：仿真全绿只是"逻辑对"，还要看
      资源是否超限（BRAM $>$80\% 就要重新设计）、
      时序是否全为正（\textbf{必须看时钟对表，不能只看域内 WNS}）、
      DRC 是否为零。三者都过才允许上板。
\end{enumerate}

\textbf{流程中有两个"不对称"值得特别说明}：

\begin{tcolorbox}[colback=gray!4, colframe=boxFrame, breakable,
                  title=\textbf{不对称一：仿真红与综合红，处理方式完全不同}]
\begin{itemize}
\item \textbf{仿真红}（第 ⑤ 步 ⟹ 回第 ③ 步）：这是\textbf{逻辑错}，
      可以定位后继续改。但有一个硬规则——\textbf{同一问题连猜 3 次不中就必须停下来}，
      用 \texttt{git checkout --} 回退到上一个绿状态重新分析。
      在红树上继续打补丁，只会把问题越搅越乱（这个教训在 SD 卡初始化
      调试时付出了一整天代价）。
\item \textbf{综合红}（资源超限 / 时序为负 / DRC 非零）：这通常\textbf{不是 bug，
      而是架构问题}。例如 BRAM 占用到 98\% 导致布线拥塞、进而
      \texttt{clk\_sys} 违例 $-1.09$\,ns、\texttt{place\_design} 直接失败——
      这时候改代码没用，必须\textbf{改架构}（换存储方案 / 降分辨率 / 拆模块）。
\end{itemize}
\end{tcolorbox}

\begin{tcolorbox}[colback=gray!4, colframe=boxFrame, breakable,
                  title=\textbf{不对称二：账本反哺的是"下一轮的规格"，不是"这一轮的代码"}]
问题账本（825 条）和技能包（4 个）不是"事后总结"，
而是在\textbf{下一轮设计的第 ① 步就被读取}。例如在做 SD 卡子系统之前，
先读了 \texttt{rtl-verification} 技能包里"永远不要在信号自己更新的沿上读它"
这一条，于是在写 \texttt{sd\_read} 的 testbench 时就\textbf{避免}了
\texttt{@(negedge sd\_clk)} 这个坑——这是把过去的失败\textbf{前置}成设计约束，
而不是等它再犯一次。
\end{tcolorbox}

\subsubsection{主要提示方式}

\textbf{方式一：给“判据”而不是“要求”}

\begin{tcolorbox}[title=\textbf{用户（原始提示词）}, colback=blue!2!white,
                  colframe=blue!30!black, fonttitle=\bfseries, breakable]
实现 SPI 模式的 SD 卡初始化：CMD0 $\rightarrow$ CMD8 $\rightarrow$
循环 (CMD55 + ACMD41) 直到 R1 的 bit0=0。\\
\textbf{判据}：① 第一次 \texttt{Go} 必须走完 5 步；
② \textbf{第二次 \texttt{Go} 也必须能重新走完}；
③ 初始化阶段卡不校验 CRC，用固定值即可。\\
\textbf{不要}：不要用状态机隐式等待，每步都要有超时计数。
\end{tcolorbox}

\begin{tcolorbox}[title=\textbf{AI 回答（要点）}, colback=green!2!white,
                  colframe=green!30!black, fonttitle=\bfseries, breakable]
生成了 5 个状态的状态机（\texttt{IDLE/CMD/WAIT/RESP/DONE}），
每条命令带 24 位超时计数。首次提交即通过 5/5 判据。
\textbf{“第二次 Go”这个判据后来救了大命}——后续调试中发现
若 \texttt{Go} 只清 \texttt{cnt} 不清 \texttt{state}，重配时会永久卡死
（\texttt{Init\_Done} 恒 0 ⟹ 音频被按住复位 ⟹ 切输入源静音 + 频谱冻住）。
\end{tcolorbox}

\textbf{方式二：要求“交叉验证”而不是“相信”}

\begin{tcolorbox}[title=\textbf{用户（原始提示词）}, colback=blue!2!white,
                  colframe=blue!30!black, fonttitle=\bfseries, breakable]
TMDS 编码器我担心记错。请你找 \textbf{2\textasciitilde 3 份独立实现}
（Xilinx 官方示例、开源核、论文附录），\textbf{逐行比对}，
把差异点列出来，再写。如果三者不一致，停下来告诉我。
\end{tcolorbox}

\textbf{结果}：找到 3 份实现，其中 2 份在“DC 平衡”分支的 \texttt{cnt} 更新条件上
写法不同但等价；确认后写入 \texttt{tmds\_enc.v}，一次通过。

\textbf{方式三：要求“量化”而不是“看起来对”}

\begin{tcolorbox}[title=\textbf{用户（原始提示词）}, colback=blue!2!white,
                  colframe=blue!30!black, fonttitle=\bfseries, breakable]
不要给“看起来合理”的结论。要求：① 实际占用/总量/百分比；
② 与优化前对比；③ 如果变差了，指出是哪一项变差；
④ 时序报告里 WNS 是正是负、最差路径在哪。

\subsubsection{从“观察”到“技能”的抽象链路}

\begin{tcolorbox}[colback=gray!4, colframe=boxFrame, breakable,
                  title=\textbf{以 \texttt{rtl-verification} 为例}]
\textbf{原始观察（账本 412）}：TB 里 \texttt{@(negedge sd\_clk)} 采样，总差一拍。\\
$\downarrow$ 追问“为什么”\\
\textbf{根因}：\texttt{sd\_clk} 由 \texttt{div\_clk} 分频而来，
\texttt{negedge sd\_clk} 恰好等于 \texttt{posedge div\_clk}，读到的是旧值。\\
$\downarrow$ 再问“是个例还是通类”\\
\textbf{聚类（账本 413/414/415）}：非阻塞赋值在同一 \texttt{always} 读不到新值；
\texttt{acmd41\_cnt} 在 CS 沿被清零导致永远回不到第 3 次；
边际推理调不动时应换显式计数。\\
$\downarrow$ 抽象成规则\\
\textbf{技能包条目}：“永远不要在信号自己更新的沿上读它”；
“复位的作用域要精确界定：跨帧状态 $\neq$ 帧内状态”。\\
$\downarrow$ 写成可执行检查\\
\textbf{判据}：写 TB 时自问——这个 \texttt{@(posedge/negedge X)}
和 X 的驱动沿是同一个吗？是则改成 \texttt{@(posedge clk); \#1;} 或换一个沿。
\end{tcolorbox}

\subsection{心得体会}
%-----------------------------------------------------------------------------

\subsubsection*{一、写 RTL 最难的不是“写”，是“验证”}

项目初期我以为难点在 RTL 本身。做完 60 个模块后才发现，
\textbf{真正耗时的是“怎么知道它是对的”}。最后的做法是：每个模块配一个 Python
定点黄金模型，逐位对拍，不允许“波形看起来差不多”。39 个 testbench 里
\textbf{至少 12 个在第一次跑就红}——而这 12 条每条都对应上板时可能花掉一两天的 bug。

印象最深的是 \texttt{sd\_img\_load}：SD 一块是 262\,144 字节，
而一帧只需 261\,120 字节，多出的 1024 字节反复写最后一个地址，
把画面右下角踩坏。这个 bug \textbf{仿真能抓到、上板极难定位}
（表现为“右下角一小块花屏”）。这就是“逐位对拍”的价值。

\subsubsection*{二、资源永远比想象中紧}

640$\times$360$\times$16\,bit 的帧缓冲算下来要 103 块 BRAM，
而器件只有 135 块。我以为“留 30 块给其它模块够了”，
实测发现加上其它器件直接到 98\%，\textbf{布线拥塞导致时序崩到 $-1.09$\,ns
（\texttt{place\_design} 直接失败）}。

后来走了四步：
① 640$\times$360$\times$8（8 位色）—— 能构建，但 256 色在渐变图上看得到明显色带，被用户否掉；
② 320$\times$180 单份（LCD 居中）—— 省资源，但 LCD 有黑边；
③ 最后用\textbf{两份不同尺寸的缓冲}：LCD 480$\times$272 全图 + HDMI 320$\times$180 裁剪区，
\textbf{总 BRAM 100.5（74\%）}，时序 +1.78\,ns。

\textbf{最大收获}：\textbf{存储压力 = 像素数 $\times$ 位深，是两个旋钮}。
我一开始只拧了“位深”这一个，走了一大圈才发现“降分辨率 + 整数倍放大”更好。

\subsubsection*{三、“能构建” ≠ “能交付”}

时序违例\textbf{不会}阻止 Vivado 生成 \texttt{.bit}——它只会报一个负的 WNS。
所以判断标准不能是“构建成功”，必须是“\textbf{所有时钟组的 WNS 都为正}”。
有一次我因为只看返回码 0 就以为成功，差点把一个 WNS $=-0.82$\,ns 的比特流烧上板。

\subsubsection*{四、调试的“三级跳”}

\begin{enumerate}
\item \textbf{第一级：看报错} —— 工具说得清清楚楚的问题（语法、端口不匹配）不要浪费时间猜；
\item \textbf{第二级：看报告} —— 综合/实现的 util、timing、DRC、CDC 报告里，
      工具其实已经把根因写出来了（如“LUT as Distributed RAM over-utilized”
      直接说明存储器没映射到 BRAM）；
\item \textbf{第三级：改设计} —— 修根因，不要修症状。同一根因可能在不同模块复发
      （同步复位问题复发了 4 次），所以\textbf{修完要全量重扫}。
\end{enumerate}

\textbf{同一问题连猜 3 次不中 ⟹ 停止猜测，换成能观测内部状态的手段}。
HDMI 撕裂我猜了 4 次（复位延迟 256 周期 / 2.6\,ms / locked AND / OSERDESE2），
全部无效。最后还是把它写进文档、标“已试过 $\times$ 无效”，
留给 ILA 或示波器——\textbf{知道什么时候该停，也是能力}。

\subsubsection*{五、关于用大模型写 RTL}

我的体会是：\textbf{大模型擅长“把已知方案写出来”，不擅长“判断方案对不对”}。

\begin{itemize}
\item 让它写一个 TMDS 编码器——写得又快又好，因为这是有标准答案的；
\item 让它判断“该用一份缓冲双读口还是两份缓冲”——它会给出一个“看起来合理”的答案，
      而真正正确的答案要靠\textbf{我自己去算 BRAM 数量、去读 UG473、去跑综合验证}；
\item 最容易出问题的是\textbf{批量修改}：\texttt{str.replace()} 找不到就静默成功，
      改完脚本报“OK”但文件根本没变。所以现在所有批量替换都强制加 \texttt{assert}。
\end{itemize}

\textbf{正确的用法是把它当“高速打字机 + 交叉验证工具”}，
而不是“决策者”。所有关键决策（架构、位宽、时序预算）必须自己算过、
自己验证过。

\subsubsection*{六、写在最后}

825 条问题账本看起来很多，但每一条背后都是一次真实的失败。
这个项目最大的资产不是那 11\,716 个 LUT，而是这份账本——
它让我在第二个类似项目里，\textbf{避开了 80\% 曾经踩过的坑}。
