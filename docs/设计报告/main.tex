\begin{abstract}
本作品在 Xilinx Artix-7 XC7A100T 上以纯 RTL（未使用 HLS、软核或任何现成 IP）实现了一套音频一体化系统，覆盖“采集 $\rightarrow$ 均衡 $\rightarrow$ 频谱分析 $\rightarrow$ 可视化 $\rightarrow$ 交互”的完整闭环。

系统以 WM8960 编解码器为音频前端（48\,kHz / 24\,bit），采样数据同时进入两条并行流水线：一是5 段定点 IIR 参量均衡器，逐段做 Q 格式与位宽预算，各段增益可在线独立调节并实时回放；二是1024 点基 2 FFT 频谱分析引擎，仅一个蝶形单元配合双口 BRAM 时分复用，硬件开销不到全并行方案的 1/512，整帧处理仅占帧周期的 1.3\%。频谱结果经对数频率分箱、峰值保持与线性衰减后驱动双路独立显示：LCD 480$\times$272 作交互界面（8 按钮面板 + 8 行状态栏），HDMI 640$\times$360 作展示大屏（80 根独立柱 + 波形），并从 SD 卡读取图片作为动态背景（LCD 1:1 满屏、HDMI 裁中心 320$\times$180 后 2 倍整数放大）。

系统横跨四个时钟域，以格雷码异步 FIFO 与电平翻转握手完成跨域传递。
所有参数可经板载按键或 UART ASCII 命令在一个时钟周期内生效。

整机占用 11\,716 LUT（18.48\%）、100.5 BRAM、26 DSP48，时序全部收敛（\texttt{clk\_sys} +1.779\,ns / \texttt{clk\_hdmi} +4.028\,ns），综合与实现 0 错误 0 警告，39 个 testbench 全部与 Python 定点黄金模型逐位对拍通过，并已通过 QSPI Flash 固化实现掉电自启动。

\keywords{音频一体化\quad  FPGA\quad  纯 RTL\quad   频谱可视化\quad  跨时钟域}
\end{abstract}

\subsection{选题背景与实际问题}
%-----------------------------------------------------------------------------

音频可视化正处在一个快速扩张的市场中。根据 Business Research Insights 2026 年发布的《Audio Visualizer Market》报告，全球音频可视化市场规模在 2026 年估计为 27.4 亿美元，该报告预计到 2035 年将增长到 116.1 亿美元，对应 2026 至 2035 年 17.4\% 的年复合增长率\cite{bri2026avm}。该报告指出，增长的主要驱动力来自媒体消费体验的持续升级、现场演出与社交媒体内容对创意可视化的需求，以及交互式显示设备的普及；同时，实时音频可视化与 AI、增强现实技术的结合也成为最新的发展趋势。这意味着可视化不再只是播放器上的一个装饰性插件，而是逐渐成为音频产品的基础能力。在此背景下，本作品选择在 FPGA 上以纯 RTL 实现一套完整的音频可视化系统。

音频可视化设备在消费市场需求广泛，例如车载音响频谱显示、直播/演出调音台可视化、Hi-Fi 播放器界面等等。此外，在工业检测领域：
如机械振动频谱监测、电机异响诊断、齿轮箱故障早期预警等案例中也经常依赖于频谱分析方法。虽然目前音频可视化技术已经非常成熟，但现有产品存在一个普遍的结构性矛盾，如\cref{tab:bg}~所示 ：

在功能清单之上，本作品有三个值得单独展开的设计选择，也体现了在实际工程中容易遇到的一些问题以及解决的方法：

\subsubsection*{（一）扫描式双路渲染：一份核心，两块屏}

常规做法是先渲染到帧缓冲，再由扫描逻辑读出，但 640$\times$360$\times$16\,bit 的帧缓冲需要 103 块 BRAM，加上其它模块更是直接达到了 98\% 左右，而本器件只有 135 块，实测会导致布线拥塞、时序更是崩到 $-1.09$\,ns、导致 \texttt{place\_design} 构建失败。

本作品把渲染核心抽象为纯组合函数 $(x, y, \text{mode}) \rightarrow$ \,RGB：

\begin{lstlisting}[language=Verilog, basicstyle=\ttfamily\zihao{6},
                   frame=single, rulecolor=\color{boxFrame}]
// 同一个模块，靠参数决定分辨率和是否画 UI
disp_top #(.HDISP(480), .VDISP(272), .WITH_UI(1)) u_disp_lcd  (...);  // 12.5 MHz
disp_top #(.HDISP(640), .VDISP(360), .WITH_UI(0)) u_disp_hdmi (...);  // 25 MHz
\end{lstlisting}

这样带来的好处主要有三重：1. LCD 侧零 framebuffer，只有 SD 图片需要存储；
2. 换分辨率只改参数，不改逻辑；3. 两路的配色、柱高、波形天然一致，因为它们看的是同一份输入数据。

\subsubsection*{（二）数据柱数与显示柱数解耦}

LCD 的像素宽为 480，使用 60 根柱则每柱 8 像素，可以整除；而 HDMI 的像素宽为 640，若也用 60 根柱则每柱 10.67 像素，无法整除，所以必须用乘法器，但是乘法器会恶化时序。

本作品把数据大小和显示柱数拆成两个独立参数（\texttt{NBARS} / \texttt{NBARS\_DISP}），HDMI 侧改用 80 根柱可以整除，只需移位。更关键的是原本路径由 \texttt{generate} 的恒等分支保护：

\begin{lstlisting}[language=Verilog, basicstyle=\ttfamily\zihao{6},
                   frame=single, rulecolor=\color{boxFrame}]
generate
    if (NBARS_DISP == NBARS) begin : g_ident
        assign bbar = dbar[AW-1:0];              // 综合器看不到除法
    end else begin : g_scale
        assign bbar = (dbar * NBARS) / NBARS_DISP;
    end
endgenerate
\end{lstlisting}

\subsubsection*{（三）三个细节层面的设计}

\begin{itemize}
\item \textbf{静音改用“送 0 数据”而不是“停 I2S”}：\texttt{data\_en} 照常拉高，只是把左右声道数据清零。这样 WM8960 收到的是“合法的 0 采样数据”，链路不会以为对端掉线，避免由静音或取消静音而产生的瞬间爆音。
\item \textbf{跨域握手用“电平翻转”而不是“单拍脉冲”}：\texttt{start} 若是单拍脉冲，跨到更慢的时钟域时可能被整个漏掉；改成翻转一个电平再双打取边沿，无论两侧时钟比多大都不会丢。
\item \textbf{按键活动标志也用电平翻转}：面板的空闲自动收起计时器需要知道“用户刚才是否有动作”，同样不能用一个拍宽的脉冲跨域。
\end{itemize}

\subsection{主要技术特点及创新点}
%-----------------------------------------------------------------------------

\subsubsection*{1. 单蝶形 FFT 的极低资源占用}

1024 点 FFT 若全并行需 512 个蝶形 $\times$ 4 乘法器 $=$ \textbf{2048 个 DSP48}，超出器件总量（240 个）近 8 倍。而本作品用一个蝶形单元加双口 BRAM 进行时分复用：

\begin{table}[H]
\centering
\caption{FFT 架构方案对比（1024 点，48\,kHz 采样）}
\label{tab:fft}
\begin{tabular}{lccccc}
\toprule[1.5pt]
\rowcolor{gray!25} 方案 & 蝶形单元 & DSP48 & BRAM & 整帧耗时 & 占帧周期 \\
\midrule[1pt]
全并行 & 512 & 2048 & 0 & 1 拍 & 0.04\% \\
4 路并行 & 128 & 512 & 0 & 7\,680 拍 & 0.3\% \\
\textbf{单蝶形（采用）} & \textbf{1} & \textbf{4} & \textbf{2} & \textbf{30\,720 拍} & \textbf{1.3\%} \\
\bottomrule[1.5pt]
\end{tabular}
\end{table}

WM8960 采样数据一帧周期大约为 46.9\,ms，而 FFT 计算整帧耗时 $30\,720 \times 20.83\,\text{ns} = 0.64$\,ms，仅占 1.3\%，余量为 75 倍。

\subsubsection*{2. 扫描式渲染，无帧缓冲}

把渲染核心抽象为纯组合函数 $(x,y,\text{mode}) \rightarrow$\,RGB，扫描到哪个像素就算哪个像素。LCD 侧无需任何 framebuffer，一帧 130\,560 个像素全部实时算出。

\subsubsection*{3. 零成本的裁剪与放大}

HDMI 侧需要从 480$\times$272 的全图中裁出中心 320$\times$180 的区域，再放大 2 倍铺满 640$\times$360。在实际操作中，可以通过两次移位相加从而避免使用到乘法器：

\begin{lstlisting}[language=Verilog, basicstyle=\ttfamily\zihao{6},
                   frame=single, rulecolor=\color{boxFrame}]
// 裁剪地址：dy*320 = dy*256 + dy*64 -> 两次移位相加，零 DSP
wire [18:0] crop_addr = (dy << 8) + (dy << 6) + dx;

// 2 倍放大：显示坐标右移 1 位 -> 一个移位，零算术
wire [XW-1:0] fb_sx = (fb_lx >> 1) + FB_CX[XW-1:0];
wire [YW-1:0] fb_sy = (fb_ly >> 1) + FB_CY[YW-1:0];
\end{lstlisting}

\subsubsection*{4. 不同尺寸双帧缓冲替代“双读口”}

两个显示器时钟不同（12.5\,MHz / 25\,MHz）。实测表明 Vivado 的 BRAM 推断不支持“1 写 2 读跨时钟”，会静默退化成分布式 RAM（LUTRAM），触发 \texttt{DRC UTLZ-1} 错误（需 86\,452 个 \texttt{RAMD64E}，仅 19\,000 个可用），加 \texttt{(* ram\_style = "block" *)} 进行约束也无效。

因此本作品改为两份不同尺寸的缓冲，即 LCD 侧直接读取 480$\times$272 的全部图像数据，HDMI 读取对应的 320$\times$180 范围内的裁剪区图像数据后进行 2 倍整数放大，这样一来 BRAM 从 116 块降到 84 块，节省一定资源的同时也避开了由静默推断而导致的错误。

\subsection{设计流程}
%-----------------------------------------------------------------------------

本作品采用的不是写完代码再补测试的传统流程，而是模型先行、逐位对拍、每轮全量回归的闭环流程，如表~\ref{fig:flow} 所示。之所以这样做是因为 RTL 调试的最大成本不在于写，而是在于如何确认怎么写才是对的。尤其是在做定点算法时，肉眼根本看不出 1 LSB 的偏差。此外，在实际设计过程中，当遇到报错时，也需要区分是仿真报错还是综合报错，以采取相应的解决办法。

\begin{tcolorbox}[colback=gray!4, colframe=boxFrame, breakable,
                    title=\textbf{仿真红与综合红的不同处理方式}]
\begin{itemize}
    \item \textbf{仿真红}：这是\textbf{逻辑存在错误}，可以定位后再继续修改。但有一个硬规则：同一问题连续修改 3 次都不对就必须停下来， 回退到上一个稳定分支重新分析。在一个错误的分支上继续修改，只会把问题越搅越乱。

    \item \textbf{综合红}：这通常并非 bug，而是架构问题。例如 BRAM 占用到 98\% 导致布线拥塞、进而产生 \texttt{clk\_sys} 的时序违例 $-1.09$\,ns、\texttt{place\_design} 直接失败。所以这时候改代码几乎没用，必须从架构上进行修改，例如换存储方案、降低分辨率。
\end{itemize}
\end{tcolorbox}

\section{系统组成及功能说明}

%-----------------------------------------------------------------------------
\subsection{整体介绍}
%-----------------------------------------------------------------------------

系统的整体结构可以总结为一条从模拟前端到双路显示的单向数据流，加上横跨四个时钟域的配置分发网络。单向数据流确保了当显示侧即使因为 SD 卡读图卡住，音频回环也照常工作；配置分发网络则保证了任一时刻两块屏的配置一致性，因为它们读的是同一组寄存器。

整个系统按时钟域以及功能可以切成四块，主要分为音频处理区（\texttt{clk\_sys} 48\,MHz）、显示渲染区（\texttt{clk\_pix} 12.5\,MHz）、HDMI 输出区（\texttt{clk\_hdmi} 25\,MHz）、存储与交互区（\texttt{clk\_sys}）。系统整体架构框图以及四块区域的功能总结分别如图~\ref{fig:arch} 和表~\ref{tab:zone} 所示。

首先，图中上半部分为音频处理区，主要包括音频采集和数据处理两部分。WM8960 将音频输入的模拟信号转换为数字信号，由 Audio-Top 模块读取和 DC-Block 模块处理后被分为两路，一路经过 FIR 低通滤波后当作波形数据送进 Disp-Top 模块进行显示，另一路则是被送进 FFT-Core 模块进行频域分析，计算后的数据再通过 spectrum 模块映射为柱状频谱送进 Display-Top 模块用于显示。

其次，图中左下角为存储与交互区，包含 SD 卡读取通道与三路交互输入。SD 卡的四根 SPI 信号经 SD-Control-Top 完成初始化与多块读取，取回的字节流由 SD-Img-Load 拼成像素写入 Frame-Buffer，再作为 DispTop 的背景源。交互方面，板载按键经 Key-UI（消抖 + 手势识别）产生光标与动作码，PC 端发送指令 UART-RX 送入 CMD-Proc 对 ASCII 命令进行解析，两者与触摸输入共同汇入 UI-Control 配置寄存器组进行统一管理，最后由 cdc-Sync 分发到各个时钟域，产生相应的动作。

最后，图中右下角为显示渲染区和 HDMI 输出区，两者共用同一份 Disp-Top 渲染核心，只是参数不同。在 Disp-Top 内部，LCD-Timing 产生扫描坐标，Bg-Src / Wave-Buf / Status-Line、Text-Buf、Font-ROM / UI-Layer / UI-Anim 五个图层模块各自接收同一组坐标独立计算，计算后的输出统一送进 Disp-Mix 与柱状频谱、极坐标频谱（Polar-Map + Rainbow-ROM）按优先级叠加，最终形成一帧像素流。该像素流分两路：一路直接驱动 LCD；另一路经 TMDS-Enc 编码与 TMDS-Out 串行化后输出 HDMI，同时 Frame-Buffer 中的 SD 图片也作为两路的背景参与合成。

\subsubsection{硬件整体介绍}

本作品没有自制的 PCB，所有电路都是开发板与现成模块的组合，大部分功能实现都集中在 FPGA 内部。整机主要由 5 个物理部件构成：

\end{enumerate}

\subsubsection{电路各模块介绍}

由于本作品没有自行设计 PCB，全部电路均都来自开发板与现成模块，因此本节按外设逐块说明各接口的电气特性、关键信号与使用注意事项。整机外围共六类电路：两路 LED 指示与三个按键（复位、KEY1、KEY2）、UART 转 USB 电路、SD 卡座、HDMI 输出电路、LCD 接口以及 WM8960 音频模块。所有外设都挂在 FPGA 的 Bank 14 与 Bank 15/16 上，其中 Bank 14 的 Vcco 固定为 3.3 V，因此该 Bank 上的信号全部按 LVCMOS33 约束。

\item \textbf{LED 与 KEY}

HDMI 部分由四对差分信号与三个控制信号组成。四对差分分别是时钟对（Y18/Y19）、数据0对（V18/V19，蓝色通道）、数据1对（AA19/AB20，绿色通道）与数据2对（V17/W17，红色通道），全部按 \texttt{TMDS\_33} 标准约束。控制信号包括 I2C 的 DDC 通道（U20/T21）、热插拔检测 HPD（V20）与输出使能 \texttt{HDMI\_OUT\_EN}（V22）。此外还有一个值得注意的细节，\texttt{HDMI\_OUT\_EN} 引脚被接到 NC7SZ125 缓冲器的输出使能脚，低电平有效，若该脚浮空导致为高电平，屏幕会表现为无信号，很容易被误判成 TMDS 编码写错，所以代码中需要固定驱动为低电平。

LCD 通过 40 pin 排线接在 JM1 扩展口，采用 RGB888 并行接口。除 24 根颜色信号外，还需要行同步 HS（C18）、场同步 VS（E18）与像素时钟 DCLK（F18），三者分别对应 JM1 的 29、32、30 脚。图中给出的 40P 座与 JM1 是 1:1 对应关系，对标签时需要先按排针的奇偶列分开，再按上下顺序读取，否则极易把相邻信号写反。

本工程未使用 LCD 的 DE 信号，而是靠 HS 与 VS 直接驱动该模组，实测可正常出图。屏幕模组型号为 TIANMA-TM043NDH02，不带触摸层，因此触摸屏驱动虽然已写好但未接入实际功能。

\item \textbf{WM8960 音频模块}

WM8960 音频模块通过杜邦线接到 JM2 扩展口，共六根信号。I2S 部分包括位时钟 BCLK（J20，3.072 MHz）、帧时钟 LRCLK（K18，48 kHz）、ADCDAT（H20，模块 $\rightarrow$ FPGA）与 DACDAT（G20，FPGA $\rightarrow$ 模块）；配置部分包括 I2C 的 SCL（K21）与 SDA（K22），全部按 LVCMOS33 约束。

关键点在于时钟方向，WM8960 的数字音频接口时钟从自身 SYSCLK 派生，手册要求 MCLK 与 BCLK、LRCLK 同源，因此该模块必然是 I2S 主设备，FPGA 只能作从设备。这意味着 BCLK 与 LRCLK 对 FPGA 而言是异步输入，本工程不把它们当作全局时钟，而是在 48 MHz 域内过采样恢复出边沿选通信号，从而少一个时钟域，也避开了时钟脚抖动的问题。

另外，该模块上电后必须通过 I2C 写入寄存器才能出声。其中模拟旁路的设置尤其关键，若旁路默认开启，音频信号会完全绕开 DSP 处理链，表现为静音功能失效、均衡器无效且只有单边喇叭出声。

\subsubsection*{1. 音频链路（\texttt{audio\_top}）}
%-----------------------------------------------------------------------------

% \textbf{接口设计：}
模块对外只有三组信号。第一组是 I2S 物理接口，包括位时钟 \texttt{bclk}、帧时钟 \texttt{lrclk}、串行输入 \texttt{sdin} 与串行输出 \texttt{sdout}，其中前三个是输入，因为 WM8960 是本系统的 I2S 主设备。第二组是控制接口，包括 5 段 × 5 bit 的增益档位 \texttt{band\_gain}、重载触发 \texttt{cfg\_load}、旁路使能 \texttt{bypass}，以及反馈状态 \texttt{cfg\_busy} 与 \texttt{running}。第三组是观测接口，\texttt{dbg\_rx\_l/r/rx\_valid} 输出的是均衡之前的原始采样，直接送给 \texttt{fft\_core} 进行下一步处理。该模块的接口定义如下：

\begin{lstlisting}[language=Verilog, basicstyle=\ttfamily\zihao{6},
                   frame=single, rulecolor=\color{boxFrame}]
module audio_top #(
    parameter integer DW    = 24,     // 样本位宽 Q1.23
    parameter integer NSECT = 5       // 均衡段数
) (
    input  wire clk,                  // clk_sys = 48 MHz
    input  wire rst_n,
    input  wire mute,                 // 1 = 静音（送全 0 采样）

    // I2S 物理接口：从模式，bclk/lrclk 由 WM8960 提供
    input  wire bclk,
    input  wire lrclk,
    input  wire sdin,                 // WM8960 ADCDAT -> FPGA
    output wire sdout,                // FPGA -> WM8960 DACDAT

    // 控制接口（必须已同步到 clk 域）
    input  wire [NSECT*5-1:0] band_gain,  // 每段 5 bit：0..20 对应 -10..+10 dB
    input  wire               cfg_load,   // 拉高即触发系数重载
    input  wire               bypass,     // 1 = 直通
    output wire               cfg_busy,
    output wire               running,

    // 观测接口：均衡之前的原始采样，送 fft_core
    output wire signed [DW-1:0] dbg_rx_l,
    output wire signed [DW-1:0] dbg_rx_r,
    output wire                 dbg_rx_valid
);
\end{lstlisting}

其中，\texttt{cfg\_load} 的作用是把 \texttt{eq\_coeff\_rom} 里对应的系数搬进两个均衡器。装载过程由一个小状态机控制，共 25 次写操作（5 段 × 5 个系数），期间 \texttt{cfg\_busy} 拉高、\texttt{running} 拉低，音频流水暂停弹出新样本，因此调整增益不会在听感上产生跳变。

\subsubsection*{2. FFT 引擎（\texttt{fft\_core}）}
%-----------------------------------------------------------------------------

该模块的接口定义如下：

\begin{lstlisting}[language=Verilog, basicstyle=\ttfamily\zihao{6},
                   frame=single, rulecolor=\color{boxFrame}]
module fft_core #(
    parameter integer N          = 1024,   // 点数
    parameter integer LOG2N      = 10,
    parameter integer DW         = 24,     // 数据位宽 Q1.23
    parameter integer TW         = 16,     // 旋转因子位宽 Q1.15
    parameter integer FIFO_DEPTH = 64
) (
    input  wire clk,                       // clk_sys = 48 MHz
    input  wire rst_n,

    // 输入样本流（实数）
    input  wire signed [DW-1:0] x_in,
    input  wire                 x_valid,

    // 输出幅度谱（前 N/2 个频点）
    output reg  [LOG2N-2:0]     y_index,   // 频点序号 0..511
    output reg  [DW:0]          y_mag,     // 幅度，多一位防溢出
    output reg                  y_valid,

    output wire                 busy,      // 1 = 正在运算
    output reg  [7:0]           drop_cnt   // 输入 FIFO 溢出计数，应恒为 0
);
\end{lstlisting}

输入端是标准的流接口，\texttt{x\_in} 配 \texttt{x\_valid} 送入实数样本；
输出端给出频点序号 \texttt{y\_index} 与对应幅度 \texttt{y\_mag}。
\texttt{drop\_cnt} 是一个自检信号，如果输入速率超过处理能力导致 FIFO 溢出，
它会计数，正常运行时必须恒为 0。

\textbf{数据流设计：}模块的内部只有一个蝶形单元，因此 1024 点所需的总蝶形数
$10 \times 512 = 5120$ 只能串行完成，状态机分三段：

\begin{enumerate}
\item \texttt{S\_IDLE}：从输入 FIFO 连续取出 1024 个样本，按位反转序写入工作 BRAM。位反转是 DIT 结构的要求，如果输入按自然序存放，蝶形的两个输入就对不上。这一步不会额外占用时间。

\item \texttt{S\_RUN}：10 级循环，每级 512 个蝶形。地址发生器同时产出三个量，分别为蝶形两点地址 \texttt{p} 与 \texttt{q}、以及旋转因子索引 \texttt{tw\_idx}。前者送入 BRAM 的 A/B 读地址，后者送入旋转因子 ROM。蝶形从 BRAM 读出两个复数点，与旋转因子做一次复数乘加，再把结果写回同一对地址，形成读、算、写回的反馈环。

\item \texttt{S\_OUT}：按自然序读出 512 个频点。
\end{enumerate}

\textbf{定点格式设计：}这是 FFT 实现中最需要仔细处理的部分，
本设计采用表~\ref{tab:fftfixed} 的位宽体系。

\begin{table}[H]
\centering
\caption{FFT 的定点格式与位宽推导}
\label{tab:fftfixed}
\begin{tabular}{p{2.2cm}p{1.6cm}p{1.2cm}p{8.0cm}}
\toprule[1.5pt]
\rowcolor{gray!25} 量 & 格式 & 位宽 & 推导依据 \\
\midrule[1pt]
输入数据 & Q1.23 & 24 & 与 I2S 24 bit 采样对齐，满幅范围 $[-1, 1)$ \\
旋转因子 & Q1.15 & 16 & $|\cos|,|\sin| \le 1$，15 位小数精度约 $3\times10^{-5}$ \\

% 其中三个细节值得说明。第一，乘法结果需要右移 15 位才能回到 Q1.23，
% 舍入采用加 $2^{14}$ 再右移的方式，即四舍五入而非截断，
% 这样可以把直流偏置误差降到最低。第二，舍入用的偏置常量必须写成
% 有符号且位宽正确的形式；如果写成 \texttt{1'sd1}，
% 那是 1 位有符号数，取值只能是 0 或 $-1$，结果会完全错误。
% 第三，蝶形输出是多一位的 25 bit，写回 BRAM 前需要饱和到 24 bit，
% 饱和处理保证了 FFT 在处理大信号时不会因溢出而反相。
%
% 每一级蝶形都会让数值增长，对 1024 点做归一化除 2 可以避免溢出，
% 本设计把这个除法合并进了旋转因子乘法后的右移中，
% 因此不需要额外的归一化步骤。

module disp_top #(

\end{lstlisting}

模块的核心输入是扫描坐标 \texttt{x} 与 \texttt{y}（由内部的 \texttt{lcd\_timing} 产生），所有渲染子模块都接收同一组坐标，各自独立判断这个像素该不该自己画、该画什么颜色，相互之间没有任何数据传递。除坐标外还有四组输入：柱高 \texttt{spec\_din}、波形 \texttt{wave\_din}与自适应门限 \texttt{wave\_th}、帧缓冲读出的 \texttt{fb\_rgb}，以及配置寄存器组 \texttt{ui\_*}。输出是一帧 RGB888 像素流，配合 HS、VS、DE 与像素时钟。

\textbf{数据流设计}。\texttt{lcd\_timing} 产生坐标与同步信号，随后分出五条支路：\texttt{bg\_src} 生成程序化背景，\texttt{wave\_buf} 取出波形值，\texttt{status\_line} 把配置状态写进 \texttt{text\_buf}（字模取自 \texttt{font\_rom}），\texttt{ui\_layer} 绘制按钮面板，\texttt{ui\_anim} 负责面板展开与色相过渡的插值。五条支路的输出全部进入 \texttt{disp\_mix}，与柱状频谱、极坐标频谱按优先级叠加。叠加顺序从低到高为：背景、柱谱、极坐标、波形、状态栏文字、按钮面板。

\textbf{高级效果设计}。渲染部分的观感主要由三个效果决定，它们的实现思路与生成 128 级彩虹表的做法一致，即先在 PC 端算出数据表，再让硬件按地址读表即可。

\begin{enumerate}
\item \textbf{彩虹配色表}。颜色由 Python 脚本 \texttt{gen\_rainbow.py} 通过 \texttt{colorsys.hls\_to\_rgb} 生成 128 级色相环，再取 0.85 的饱和度、 0.6 的亮度，将结果输出为 \texttt{rainbow\_rom.v} 里中。因此 RTL 侧只需输入 7 bit 地址即可得到 RGB 值。

\item \textbf{滚动色相漂移}。为了让画面产生“流动”的感觉，色相地址上叠加了一个随时间递增的偏移量 \texttt{hue\_off}。递增节奏由 \texttt{hue\_spd} 控制，实现方式是通过位掩码：\texttt{tick\_mask = (1 << (8 - hue\_spd)) - 1}。此后每帧对 \texttt{frame\_cnt} 加一，当 \texttt{frame\_cnt} 的低若干位全为 1 时 \texttt{hue\_off} 加一。这样 7 档速度分别对应每 1、2、4 … 128 帧漂移一级，无需任何除法器。这里有一个容易写错的地方：条件必须写成位与的结果全 1，若直接写成相等判断，则 256 帧才命中一次，色相几乎不动。

\item \textbf{波形自适应门限}。波形的稳定显示依赖触发，而固定门限在安静时完全无法触发。本设计用 \texttt{env\_track}跟踪音频包络并给出自适应门限，再在 \texttt{disp\_top} 内部把它钳位在 32768 到 131072 之间。下限保证安静时也能正常触发，上限防止大音量时门限过高而产生多条波形重叠的假象。
\end{enumerate}

%-----------------------------------------------------------------------------
\subsubsection*{4. SD 卡图片通道}
%-----------------------------------------------------------------------------

该通道的接口分为两级。底层是 \texttt{sd\_ctrl\_top}，它对外暴露 SPI 物理引脚与一字节一拍的读数据流，接口的定义如下：

\begin{lstlisting}[language=Verilog, basicstyle=\ttfamily\zihao{6},
                   frame=single, rulecolor=\color{boxFrame}]
module sd_ctrl_top #(
    parameter integer CLK_HZ   = 48_000_000,
    parameter integer FAST_DIV = 4,        // 高速档 48M/4 = 12 MHz
    parameter integer INIT_HZ  = 200_000,  // 初始化阶段 SPI 时钟
    parameter integer BLOCKS   = 510       // 一次读多少块
) (
    input  wire        clk,                // clk_sys
    input  wire        rst_n,

    // SD 卡 SPI 引脚
    output wire        sd_clk,
    output reg         sd_cs,
    output reg         sd_mosi,
    input  wire        sd_miso,

    // 用户接口
    input  wire        rd_start,           // 单拍脉冲：开始读
    input  wire [31:0] rd_sec_addr,        // 起始扇区
    output wire        rd_busy,
    output wire        rd_valid,           // 单拍，rd_data 有效
    output wire [7:0]  rd_data,
    output wire        init_done
);
\end{lstlisting}

上层是 \texttt{sd\_img\_load}，把字节流拼成 16 bit 像素并同时写两份帧缓冲，整个过程大致分七步：

% 两级之间的握手很轻：\texttt{sd\_ctrl\_top} 每收到一个字节就拉一拍 \texttt{rd\_valid}，\texttt{sd\_img\_load} 用这个脉冲推进像素计数器，因此无论 SD 读多慢都不会丢数据。

\begin{enumerate}
\item 首先将时钟切换到 400 kHz。SD 卡上电后必须以此速率完成初始化，超过则不响应。
\item 发送 CMD0，让卡进入 SPI 模式。
\item 发送 CMD8 查询电压范围，返回 R7 确认卡为 v2.0 及以上。
\item 循环发送 CMD55 与 ACMD41，直到 R1 的第 0 位变为 0。
      这一步必须支持重入，因为切换输入源时会重新初始化。
\item 时钟切回 25 MHz。
\item 发送 CMD18 连续读取 510 块。每块 512 字节，合计 261120 字节，正好是一帧 480×272×2 的数据量。一块读完后不回发命令，直接等待下一个数据令牌。
\item \texttt{sd\_img\_load} 拼像素并写帧缓冲，写满一帧后拉高 \texttt{done}。这里必须用 \texttt{done} 做门控停止接收，否则超出一帧的字节会反复写最后一个地址，把画面右下角踩坏。
\end{enumerate}

% 由于 LCD 与 HDMI 的分辨率不同且处于不同时钟域，
% 帧缓冲采用两份不同尺寸的实例（480×272 供 LCD，320×180 中心裁剪供 HDMI），
% 写侧共用同一个字节流，只是第二份只在裁剪区内写入。
% 这样既避免了同一块存储器被两个时钟读导致的推断失败，也把 BRAM 占用
% 从 116 块降到 84 块。

\begin{lstlisting}[language=Verilog, basicstyle=\ttfamily\zihao{6},
                   frame=single, rulecolor=\color{boxFrame}]
module sd_img_load #(
    parameter integer W  = 480,
    parameter integer H  = 272,
    parameter integer EN_CROP = 1,   // 是否同时写裁剪缓冲
    parameter integer CX = 80,       // 裁剪区左上角
    parameter integer CY = 46,
    parameter integer CW = 320,
    parameter integer CH = 180
) (
    input  wire        clk,
    input  wire        rst_n,
    input  wire        start,         // 开始新一帧
    input  wire        byte_valid,    // 来自 sd_ctrl_top 的 rd_valid
    input  wire [7:0]  byte_data,

    output reg         wr_en,         // 第一份：全图
    output reg  [18:0] wr_addr,
    output reg  [15:0] wr_data,

    output reg         wr2_en,        // 第二份：仅裁剪区
    output reg  [18:0] wr2_addr,

    output reg         done,          // 一帧写满
    output reg  [18:0] pix_cnt
);
\end{lstlisting}

\begin{table}[H]

\begin{tabular}{cp{4.0cm}ccccc}
\toprule[1.5pt]
\rowcolor{gray!25} 方案 & 存储 & 每份 & 份数 & 总 BRAM & WNS & 结论 \\

四个方案的取舍反映了一次完整的工程决策过程：

\begin{itemize}
\item \textbf{方案 A：} 是最直接的想法（存两份全图），但一算 BRAM 就发现装不下，所以这一步应该在动手之前算，而不是综合失败之后算。
\item \textbf{方案 B：}8 位色在资源上可行，甚至能构建成功，但上板后渐变图上的色阶严重到不可接受。
\item \textbf{方案 C：}只需存 320$\times$180 一份数据，最省资源，但 LCD 上片只占中间一小块、四周是背景色，观感较差。
\item \textbf{方案 D：} 最终胜出，两部分各存一份适合自己大小的数据，节省资源的同时也能满足时序要求。
\end{itemize}

其中，还有一个细节，为什么没用一个缓冲两个读口？事后发现，Vivado 的 BRAM 推断不支持 1 写 2 读跨时钟，会退化成 LUTRAM 并触发 \texttt{DRC UTLZ-1}（需要 86\,452 个 \texttt{RAMD64E}，而器件只有 19\,000 个）。后面即使尝试加上 \texttt{(* ram\_style = "block" *)} 也无法改变。

\aichat{A-01}{定点格式设计}
%---------------------------------------------------------------

\begin{tcolorbox}[title=\textbf{用户提示词}, colback=blue!2!white,
                  colframe=blue!30!black, fonttitle=\bfseries, breakable]
我在做 5 段双二阶 IIR 均衡器，输入是 WM8960 的 24 bit 采样，系数想用 18 bit。请帮我做位宽预算，要求：\\
1. 每一级的中间结果位宽都要有推导依据，不能只给结论；\\
2. 说明舍入用四舍五入还是截断，各自对直流偏置的影响；\\
3. 说明饱和放在哪一级，为什么不在每一级都饱和；\\
4. 给出一个可以自查的方法，让我能验证位宽确实够用。
\end{tcolorbox}

\begin{tcolorbox}[title=\textbf{AI 回答要点}, colback=green!2!white,
                  colframe=green!30!black, fonttitle=\bfseries, breakable]
数据 Q1.23 与系数 Q2.16 相乘得 Q3.39，两个乘积相加再留 1 位给舍入得 41 bit；
状态寄存器取 48 bit 留足余量。舍入采用加 $2^{15}$ 再右移 16，
即四舍五入，相比截断可以把直流偏置从约 $-0.5$ LSB 压到 $\pm 0.5$ LSB 以内。
饱和只放在最后一级输出，中间级不饱和，原因是逐级饱和会在强信号下
产生非线性失真，而最后一级饱和只是限幅。
自查方法：用扫频正弦输入，对比 RTL 输出与 Python 双精度参考的
最大绝对误差，若小于 1 LSB 即认为位宽足够。

下面是舍入与饱和在 RTL 里的写法，以及与之对应的 Python 参考实现：

\begin{ai_verilog}
localparam [AW-1:0] RND = {{(AW-1){1'b0}}, 1'b1} << (SH-1);  // 2^15

wire signed [AW-1:0] accr = acc + RND;      // 先加偏置，再右移
wire signed [AW-1:0] ysh  = accr >>> SH;    // 算术右移，保留符号
\end{ai_verilog}

\begin{ai_python}
def sat24(v: int) -> int:
    # 饱和到 24 bit signed，对应 RTL 里的 MAXV/MINV 比较
    if v > SAMPLE_MAX:      # +8388607
        return SAMPLE_MAX
    if v < SAMPLE_MIN:      # -8388608
        return SAMPLE_MIN
    return v
\end{ai_python}
\end{tcolorbox}

% \textbf{最终结果}：采纳，无修改。按此方案实现的 \texttt{eq\_cascade} 最终以 18 bit 系数、48 bit 累加器工作，扫频测试的频响误差小于 0.5 dB，与 Python 黄金模型逐位一致。

\aichat{A-02}{滤波器结构选择}
%---------------------------------------------------------------

\begin{tcolorbox}[title=\textbf{用户提示词}, colback=blue!2!white,
                  colframe=blue!30!black, fonttitle=\bfseries, breakable]
5 段均衡器，我打算这样分配：两段低架、一段 8 kHz 的 peaking、两段高架。请评估这个结构：\\
1. 频段之间是否会有明显的相互影响；\\
2. 级联顺序对数值条件数有什么影响，建议怎么排；\\
3. 一阶低架和二阶低架在这种场合哪个更合适。
\end{tcolorbox}

\begin{tcolorbox}[title=\textbf{AI 回答要点}, colback=green!2!white,
                  colframe=green!30!black, fonttitle=\bfseries, breakable]
相邻段的中心频率若相差不到一个倍频程，增益会相互影响，建议把相邻段拉开到 1.5 个倍频程以上。级联顺序建议按 Q 值从低到高排列，即低频架在前、peaking 居中、高频架在后，这样中间状态的动态范围最小，最不容易在定点实现中溢出。一阶低架在高频段的衰减斜率只有 6 dB/oct，若只需要粗略的低频提升就够用；二阶可以得到 12 dB/oct 并带 Q 控制，但系数灵敏度更高，需要更宽的位宽。

按上述建议改写后的频段分配如下（Python 端的设计代码，仅保留结构部分）：

\begin{ai_python}
BANDS_HZ = [100.0, 300.0, 1000.0, 3000.0, 8000.0]   # 相邻段 > 1.5 倍频程
BAND_Q   = 1.0
FS       = 48000.0

def design_band(band_idx, gain_db):
    f0 = BANDS_HZ[band_idx]
    # band0: 一阶低架。二阶低架分母在近 DC 处相位抵消严重，
    #        18 bit 系数不够（实测频响误差 1.4 dB）
    if band_idx == 0:
        return first_order_low_shelf(f0, FS, 10 ** (gain_db / 20))
    # band1~4: 二阶 peaking。DC 与 Nyquist 增益恰为 1，不干扰相邻段；
    #          band4 若用二阶高架，b0 会到 2.12 超出 Q2.16 的 [-2,2) 范围
    return peaking_eq(f0, FS, BAND_Q, gain_db)
\end{ai_python}
\end{tcolorbox}

% 这段代码体现了两个由定点约束倒推出来的选择：第一段用一阶而非二阶低架，
% 是因为二阶的分子在近直流处与 $w_0^2$ 同阶，与分母存在极强的相位抵消，
% 18 bit 系数无法表达；最后一段用 peaking 而非高架，
% 是因为高架的 $b_0$ 在 48 kHz 采样率下会达到 2.12，超出 Q2.16 的表示范围。
%
% \textbf{实际结果}：部分采纳。原本设计的 4 段改为 5 段，
% 在 8 kHz 处增加了一个二阶 peaking 段，用来压制齿音；
% 级联顺序按建议改成低架、peaking、高架的顺序。
% 最终 5 段的频响与理论值误差小于 0.5 dB。

\aichat{A-03}{FFT 架构权衡}
%---------------------------------------------------------------

\begin{tcolorbox}[title=\textbf{用户提示词}, colback=blue!2!white,
                  colframe=blue!30!black, fonttitle=\bfseries, breakable]
我需要 1024 点 FFT，采样率 48 kHz，器件只有 240 个 DSP48。请对比三种架构并给出选择依据：
1. 全并行；2. 4 路并行；3. 单蝶形时分复用。
要求每种都算出 DSP 用量、BRAM 用量、整帧耗时，并算出占帧周期的百分比。另外说明：为什么这个百分比比“绝对耗时”更重要。
\end{tcolorbox}

\begin{tcolorbox}[title=\textbf{AI 回答要点}, colback=green!2!white,
                  colframe=green!30!black, fonttitle=\bfseries, breakable]
全并行需要 512 个蝶形乘 4 个乘法器共 2048 个 DSP48，超出器件总量 8 倍，直接排除。4 路并行需要 512 个 DSP48，仍然超出 240 的上限。单蝶形需要 4 个 DSP48、2 块 BRAM，整帧 30720 拍即 0.64 ms，占 46.9 ms 帧周期的 1.3\%，余量 75 倍。百分比比绝对耗时更重要，因为 FFT 是周期性任务，只要能在下一个帧周期到来前算完就不会丢数据；剩余的时间可以全部让给其它逻辑，而 FPGA 的资源是分时共享的。

单蝶形方案的关键是地址发生器必须用位操作算出蝶形点对，不能有除法或取模，否则会引入 DSP 并恶化时序：

\begin{ai_verilog}
// 第 stage 级：把 cnt 的二进制位中间插一位
assign p = ((cnt_x >> stage_w) << sh_p) | (cnt_x & lo_mask);  // 插 0
assign q = p | (ONE << stage_w);                             // 插 1
assign tw_idx = (cnt & lo_mask[LOG2N-2:0]) << sh_tw;         // 因子索引
\end{ai_verilog}
\end{tcolorbox}

% \textbf{实际结果}：采纳，采用单蝶形方案。实际综合出来 1004 LUT、126 FF、2 块 BRAM36、4 个 DSP48，整帧 0.64 ms，与预估一致。2048 个频点与 \texttt{numpy.fft} 逐位一致。

\aichat{A-04}{跨时钟域方案}
%---------------------------------------------------------------

\begin{tcolorbox}[title=\textbf{用户提示词}, colback=blue!2!white,
                  colframe=blue!30!black, fonttitle=\bfseries, breakable]
我有三处跨时钟域：\\
1. 60 根柱高每根 9 bit，从音频域传到显示域；\\
2. 十几个配置位（模式、视图、速度），方向同上；\\
3. SD 卡读启动信号，是一个单拍脉冲，从 48 MHz 传到 25 MHz。\\
请分别给出推荐的跨域方式，并说明为什么不统一用同一种。特别说明：如果我图省事，全部用两级触发器，会出什么问题。
\end{tcolorbox}

\begin{tcolorbox}[title=\textbf{AI 回答要点}, colback=green!2!white,
                  colframe=green!30!black, fonttitle=\bfseries, breakable]
第一处是多比特总线，不能逐位双打，因为各位的传播延迟不同，会出现某些位已经更新、某些位还停留在旧值的“半新半旧”状态，接收侧可能采到一个从未存在过的数值。应当用异步 FIFO，把整帧数据作为一个原子单位传递，本设计用格雷码指针的 \texttt{async\_fifo}。第二处是慢变的单比特或小向量，用两级触发器即可，延迟两拍对配置生效时间没有影响。第三处是单拍脉冲，如果直接双打，当脉冲宽度小于目标时钟周期时会被整个漏掉，必须先把事件转换成电平状态（翻转一次），再在目标域双打并检测边沿。

三种方式的代码骨架如下。第一种是双打（用于配置位）：

\begin{ai_verilog}
(* ASYNC_REG = "TRUE" *) reg [1:0] sync_q;   // 综合器放同一片 SLICE
always @(posedge clk) sync_q <= {sync_q[0], din};
assign dout = sync_q[1];
\end{ai_verilog}

第二种是电平翻转加边沿检测（用于单拍脉冲）：

\begin{ai_verilog}
// 源域：把事件变成电平状态
always @(posedge clk_src) if (pulse) tog <= ~tog;

// 目的域：双打后取异或，得到一拍宽的脉冲
always @(posedge clk_dst) sync <= {sync[1:0], tog};
assign pulse_dst = sync[2] ^ sync[1];
\end{ai_verilog}

第三种是格雷码指针（用于多比特总线）。格雷码保证相邻两个值
只差一位，采样时最多错一位，不会出现中间态：

\begin{ai_verilog}
function [PW-1:0] bin2gray;      // g = b ^ (b >> 1)
    input [PW-1:0] b;
    begin bin2gray = b ^ (b >> 1); end
endfunction
\end{ai_verilog}
\end{tcolorbox}

% \textbf{实际结果}：部分采纳。前两处按建议实施，第三处原本打算用格雷码 FIFO，改为电平翻转加双打加边沿检测，因为启动信号只需要传一个事件，不需要传数据。后续 SD 卡读图测试 4/4 通过。

\aichat{A-05}{显示架构}
%---------------------------------------------------------------

\begin{tcolorbox}[title=\textbf{用户提示词}, colback=blue!2!white,
                  colframe=blue!30!black, fonttitle=\bfseries, breakable]
我要同时驱动 LCD 480×272 和 HDMI 640×360，两块屏显示同样的内容，但 HDMI 不要 UI。请对比两种架构：\\
1. 先渲染到 framebuffer，再分别以两个时钟读出；\\
2. 渲染核心写成纯组合函数 $(x,y) \rightarrow$ RGB，实例化两份。\\
要求算出方案 1 在 16 位色下的 BRAM 占用，并判断器件是否装得下。另外说明方案 2 在“加新图层”时的代价。
\end{tcolorbox}

\begin{tcolorbox}[title=\textbf{AI 回答要点}, colback=green!2!white,
                  colframe=green!30!black, fonttitle=\bfseries, breakable]
方案 1 若以最大分辨率 640×360、16 位色存储，需 230400 像素即约 3.68 Mbit，按每块 BRAM36 可存 36 Kbit 计算需要 103 块，而该器件只有 135 块，加上其它模块必然超出。方案 3 的渲染核心不含任何状态，LCD 侧完全不需要帧缓冲，只有 SD 图片需要真实存储。加新图层时，方案 1 需要在渲染阶段插入并重新计算整个 framebuffer，方案 2 只需新增一个模块并在混色器里排一下优先级，已有逻辑完全不动。代价是方案 2 需要在两个时钟域各跑一份相同的组合逻辑，LUT 用量约为方案 1 的两倍，但本设计 LUT 余量充足。

多柱数映射时要注意：老路径必须用结构而非数学保证零变化。下面的 generate 恒等分支让综合器在 LCD 路径上根本看不到除法，从而保证资源与改动前完全一致：

\begin{ai_verilog}
generate
    if (NBARS_DISP == NBARS) begin : g_ident
        assign bbar = dbar[AW-1:0];            // 综合器看不到除法
    end else begin : g_scale
        assign bbar = (dbar * NBARS) / NBARS_DISP;
    end
endgenerate
\end{ai_verilog}
\end{tcolorbox}

\subsubsection{智能体工作流设计}

整个开发过程不是“让模型生成一段代码然后人工检查”，而是让模型处在一个可以自行验证的闭环里。闭环的核心是三个动作的重复：改代码、跑工具、读报告。其中“跑工具”包含三层检查，任何一层不通过都不允许进入下一层。

\begin{enumerate}
\item 第一层是仿真。39 个 testbench 并行跑完约 1 分 30 秒，结果要么全绿，要么明确指出是哪个模块的哪条判据失败。这一层抓的是逻辑错误，包括数值精度、协议时序、跨域采样。
\item 第二层是静态检查。Verilator 补 iverilog 的盲区，能发现多重驱动、组合环、锁存器推断这类仿真跑不出来但上板必炸的问题。Verible 则保证代码风格一致。
\item 第三层是综合与实现。这一层不看代码，只看报告：资源是否超过 80\%、时序是否所有时钟对都为正、DRC 是否为零。
\end{enumerate}

三层都过之后才提交并上板。如果任何一层不通过，则根据失败的层级走不同的分支：仿真红说明是逻辑错，需要在本文件内定位（grep 报告、读波形），定位到根因后回到改代码；综合红通常不是 bug 而是架构问题，需要先分析 post\_route 的 util 与 timing 报告，判断是资源超限、时序不收敛还是 DRC 违规，再决定是改代码还是改架构。两条分支互不干扰，智能体工作流程如
图~\ref{fig:agentflow} 所示 。

图中两条虚线是两种失败的回退路径。左侧红色虚线对应仿真失败，通常可以在当前文件内定位；右侧蓝色虚线对应综合失败，往往意味着要重新审视架构。

\subsection{心得体会}
%-----------------------------------------------------------------------------

\subsubsection*{1. 写 RTL 最难的不是写，在于如何验证}

项目初期我以为难点在 RTL 本身。但是做完后才发现，真正耗时的是“怎么知道它是对的”。最后发现一个比较好的做法是给每个模块配一个 Python 定点黄金模型，逐位对拍，比人眼波形来的更精确。

其中印象最深的是在写 \texttt{sd\_img\_load} 模块时：SD 一块是 262\,144 字节，而一帧只需 261\,120 字节，多出的 1024 字节反复写最后一个地址，会把画面右下角踩坏。而这个 bug 仿真能抓到，但上板难以看出，这就是逐位对拍的价值。

\subsubsection*{2. 有些资源远比想象中紧}

640$\times$360$\times$16\,bit 的帧缓冲算下来要 103 块 BRAM，而器件只有 135 块。我以为留 30 块给其它模块够了，但实际发现加上其它器件直接到了 130 块（98\%），布线拥塞导致时序崩到 $-1.09$\,ns，\texttt{place\_design} 直接失败。

之后一共走了三步才得到解决：
\textbf{1.} 采用 640$\times$360$\times$8（8 位色）： 能构建，但 256 色在渐变图上看得到明显色带，被用户否掉；
\textbf{2.} 采用 320$\times$180 单份（LCD 居中）： 省资源，但 LCD 有黑边；
\textbf{3.} 最后用两份不同尺寸的缓冲：LCD 使用 480$\times$272 全图 + HDMI 做 320$\times$180 的区域裁剪后放大，最终使用 BRAM 100.5 块（74\%），时序 +1.78\,ns。

% \textbf{最大收获}：\textbf{存储压力 = 像素数 $\times$ 位深，是两个旋钮}。我一开始只拧了“位深”这一个，走了一大圈才发现“降分辨率 + 整数倍放大”更好。

\subsubsection*{3. 能构建 ≠ 能交付}

时序违例不会阻止 Vivado 生成 \texttt{.bit}，它只会报一个负的 WNS。所以判断标准不能是“构建成功”，而是必须“所有时钟组的 WNS 都为正”。之前因为看到生成了烧录文件就以为成功，差点把一个 WNS $=-0.82$\,ns 的比特流烧上板。

\subsubsection*{4. 调试的三步走}

\begin{enumerate}
\item \textbf{第一级：看报错} ，语法检查工具说得清清楚楚的问题不应浪费时间去猜；
\item \textbf{第二级：看报告}，综合/实现的 util、timing、DRC、CDC 报告里，工具其实已经把根因写出来了（如“LUT as Distributed RAM over-utilized”直接说明存储器没映射到 BRAM）；
\item \textbf{第三级：改设计}，要从根因上修，不能只看症状，同一根因可能在不同模块复发，所以修完还要全量重扫。
\end{enumerate}

\subsubsection*{5. 关于用大模型写 RTL}

这一块给我的体会是：大模型擅长把已知方案写出来，不擅长判断方案对不对、好不好。例如：

\begin{itemize}
\item 让它写一个 TMDS 编码器，它写得又快又好，因为这是有标准答案的；
\item 让它判断“该用一份缓冲双读口还是两份缓冲”，它会给出一个看起来合理的答案，而真正正确的答案还要靠算 BRAM 数量、去读 UG473、去跑综合验证。
\end{itemize}

正确的用法是把它当“高速打字机 + 写验证脚本工具”，而不是“决策者”。所有关键决策（架构、位宽、时序预算）必须自己算过、自己验证过。

\begin{lstlisting}[language=bash, basicstyle=\ttfamily\zihao{6},
                   frame=single, rulecolor=\color{boxFrame}]
vivado -mode batch -source scripts/vivado/build.tcl \
       -tclargs xc7a100tfgg484-2 top constrs

\end{lstlisting}

\subsubsection{步骤 6：准备 SD 卡（需要 \texttt{sudo}）}
\begin{lstlisting}[language=bash, basicstyle=\ttfamily\zihao{6},
                   frame=single, rulecolor=\color{boxFrame}]
lsblk -o NAME,SIZE,TYPE,TRAN | grep -E "sd|mmc"     # 找到读卡器，如 sda

# 先 dry-run（强烈建议）
python3 scripts/sdcard/mkimage.py --dry-run /dev/sda img1.png img2.png img3.png
# 预期每张图 261120 字节 = 480x272x2  <-- 数字对了就说明格式正确

# 正式写入（脚本内建系统盘保护）
echo YES | sudo python3 scripts/sdcard/mkimage.py /dev/sda img1.png img2.png img3.png
\end{lstlisting}

\subsubsection{步骤 7：上板}
\begin{lstlisting}[language=bash, basicstyle=\ttfamily\zihao{6},
                   frame=single, rulecolor=\color{boxFrame}]
# 1) 验证 JTAG
vivado -mode batch -source scripts/vivado/program.tcl -tclargs detect
# 预期：发现 JTAG 目标 ... 认到目标器件 xc7a100t

# 2) 下载到 SRAM（10 秒，掉电即失，开发期用这个）
vivado -mode batch -source scripts/vivado/program.tcl

# 3) 固化到 Flash（43 秒，掉电保持，定型后才用）
vivado -mode batch -source scripts/vivado/program.tcl -tclargs flash
# 预期：Mfg ID ef / Erase-Program-Verify successful
# 注意：JTAG 优先于 QSPI，验证 Flash 启动必须拔掉 JTAG 线再上电
\end{lstlisting}
