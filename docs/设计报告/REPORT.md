# 1. 选题背景与创新点

## 1.1 为什么选这个题目

### 1.1.1 一类真实存在的工程问题

音频可视化设备在消费市场需求广泛，例如车载音响、直播间、演出控制台等等。此外，在工业检测领域：
如机械振动频谱监测、电机异响诊断等问题中也经常依赖于频谱分析方法。虽然目前音频可视化技术已经非常成熟，但现有产品存在一个普遍的结构性矛盾：

| 现状 | 问题 |
|---|---|
| PC + 声卡 + 上位机软件 | 延迟高（10~100 ms），功耗大，不适合嵌入式部署 |
| MCU + DSP 库（如 CMSIS-DSP） | 算力不足，1024 点 FFT + 5 段 EQ + 双屏驱动无法同时满足 |
| 现成 SoC（如 Zynq + PYNQ） | 依赖 HLS/Python 框架，**底层时序不可控、启动时间长（秒级）** |
| 商用 ASIC 方案 | 功能固定，无法在线调参，不便于教学与研究 |

**核心矛盾**：**"实时性"和"可调性"难以兼得**。
专用 ASIC 实时但不灵活；软件方案灵活但延迟大。

### 1.1.2 本作品要解决的问题

用 **纯 RTL 在低端 FPGA（Artix-7 100T）上实现一条完整的、端到端延迟可预测的
音频处理链路**，做到：

- **确定性延迟**：从 ADC 采样到 LCD 像素输出，延迟以**时钟周期**计（可精确算出），
  不受操作系统调度、缓存命中率影响
- **在线可调**：所有参数（EQ 各段增益、配色、刷新率、视图）都可经按键或 UART
  在**一个时钟周期内**生效
- **零 IP 依赖**：从 I2C 主机、I2S 从机、FFT 蝶形、SDRAM/BRAM 控制器、
  TMDS 编码器到 5:1 串行化，**全部手写**，可逐行审计

### 1.1.3 前人做过什么

| 方向 | 代表工作 | 本作品的差异 |
|---|---|---|
| FPGA 音频 EQ | 多数用 Xilinx FIR Compiler / IIR Compiler IP | **手写二阶节级联**，逐段做 Q 格式与位宽预算，可解释每一位的精度来源 |
| FPGA FFT | Xilinx FFT IP（AXI4-Stream） | **手写基 2 DIT + 单蝶形时分复用**，资源仅为全并行方案的 1/512 |
| FPGA 频谱可视化 | 多为固定柱数、PC 侧渲染 | **扫描式"算到哪显示到哪"**，无 framebuffer，柱数与分辨率均可参数化 |
| FPGA HDMI | 多用现成 IP 或 VHDL 开源核 | **手写 TMDS 编码器 + OSERDESE2 原语**，逐行对照 3 份独立实现验证 |
| 开发方法 | 传统"写码—仿真—上板" | **引入大模型协作 + 问题账本 + 技能包三级沉淀**（见第 5、6 章） |

## 1.2 创新点

### 创新点一：扫描式双路渲染，无帧缓冲的实时可视化

**传统做法**：先把画面渲染到 framebuffer，再由扫描逻辑读出。
**代价**：一帧 640×360×16 bit = 103 块 BRAM，本器件只有 135 块。

**本作品做法**：把渲染核心抽象为纯组合函数 `(x, y, mode) → RGB`，
**扫描到哪个像素就算哪个像素**：

```verilog
// 一个 MMCM、一个渲染函数、两份实例 —— 分辨率完全由参数决定
disp_top #(.HDISP(480), .VDISP(272), .WITH_UI(1)) u_disp_lcd  (...);  // 12.5 MHz
disp_top #(.HDISP(640), .VDISP(360), .WITH_UI(0)) u_disp_hdmi (...);  // 25 MHz
```

**收益**：LCD 侧零 framebuffer（50 行极坐标查表 + 组合逻辑即可），
只有 SD 图片背景需要真存储。

### 创新点二：单蝶形 FFT 的极低资源占用

1024 点 FFT 若全并行需要 512 个蝶形单元 × 4 乘法器 = 2048 个 DSP，
**超出器件总量（240 个）8 倍**。

本作品用**一个蝶形单元 + 双口 BRAM 的 in-place 时分复用**：

| 指标 | 全并行方案 | 本作品 | 比值 |
|---|---|---|---|
| 蝶形单元 | 512 | **1** | **1/512** |
| DSP48 | 2048 | **4** | 1/512 |
| BRAM | 0 | 2 | —— |
| 整帧耗时 | 1 拍 | 30,720 拍 | —— |
| 占帧周期（48 kHz / 1024 点 = 46.9 ms） | 0.04% | **1.3%** | 仍余 75 倍 |

### 创新点三：数据柱数与显示柱数解耦

LCD 480 像素宽，若 60 根柱则每柱 8 像素；HDMI 640 像素宽，若 60 根柱则
每柱 10.67 像素（**不整除 ⟹ 必须用乘法**）。

本作品把「**有多少数据**」和「**显示多少根柱**」拆成两个参数：

```verilog
disp_mix #(.NBARS(60), .NBARS_DISP(80))   // 60 组数据映射到 80 根显示柱
```

并用 `generate` 的**恒等分支**保证老路径零变化：

```verilog
generate
    if (NBARS_DISP == NBARS) begin : g_ident
        assign bbar = dbar[AW-1:0];              // 综合器看不到除法 ⟹ 结构上保证零变化
    end else begin : g_scale
        assign bbar = (dbar * NBARS) / NBARS_DISP;
    end
endgenerate
```

### 创新点四：不同尺寸的双帧缓冲替代"双读口"

**问题**：LCD（`clk_pix` 12.5 MHz）和 HDMI（`clk_hdmi` 25 MHz）要读同一张 SD 图片，
但时钟不同域。直觉做法是给 BRAM 加第二个读口。

**实测**：Vivado 的 BRAM 推断**不支持"1 写 2 读跨时钟"**，会静默退化成
分布式 RAM（LUTRAM），导致 `DRC UTLZ-1`：需要 86,452 个 `RAMD64E`，
只有 19,000 个可用。**加 `(* ram_style = "block" *)` 也无效**（属性只是建议，
访问模式才决定映射）。

**本作品方案**：不用一个缓冲两个读口，而是**两份不同尺寸的缓冲**：

| 缓冲 | 尺寸 | BRAM | 用途 |
|---|---|---|---|
| `u_fb_lcd` | 480×272 RGB565 | 58 | LCD 1:1 满屏 |
| `u_fb_hdmi` | 320×180 RGB565 | 26 | HDMI 中心裁剪后 2× 放大 |

写侧共用 `sd_img_load`：每像素都写第一份，只有落在 `[80,400)×[46,226)` 的
才写第二份（用行列计数器判断，**乘 320 拆成两次移位相加 ⟹ 零 DSP**）。

**收益**：BRAM 从 116 块（两份全图）降到 84 块，**省 32 块**。

### 创新点五：三级知识沉淀的开发方法

| 层级 | 载体 | 规模 | 作用 |
|---|---|---|---|
| **问题账本** | `docs/08-skills-index.md` | **825 条** | 每条 = 现象 / 根因 / 修复 / 量化改善 |
| **技能包** | `.pi/skills/*/SKILL.md` | **4 个** | 可复用的方法论（定点 DSP / RTL 流程 / 验证 / 贡献）|
| **状态快照** | `docs/14-status-snapshot.md` | 1 份 | 随时可查"能用的 / 受限的 / 待办的" |

## 2.3 时钟架构

| 时钟 | 频率 | 来源 | 承载逻辑 |
|---|---|---|---|
| `clk_sys` | **48 MHz** | MMCM1（VCO 900 MHz ÷ 18.75）| 音频、EQ、FFT、频谱、控制、UART |
| `clk_pix` | **12.5 MHz** | MMCM1（900 ÷ 72）| LCD 扫描 |
| `clk_hdmi` | **25 MHz** | MMCM2（VCO 1000 MHz ÷ 40）| HDMI 像素 |
| `clk_5x` | **125 MHz** | MMCM2（1000 ÷ 8）| TMDS 5:1 串行化 |
| BCLK | 3.072 MHz | **外部**（WM8960）| 不当时钟用，只由 `i2s_slave_clk` 过采样 |

**关键设计决策**：**BCLK/LRCLK 不接全局时钟网络**，而是当作数据信号在
`clk_sys` 域过采样出边沿选通。这样：

- 少一个时钟域（跨域逻辑减半）
- 避开时钟脚上的抖动和相位不确定
- 代价：需要 4 倍过采样（48 MHz / 3.072 MHz ≈ 15.6 倍，余量充足）

# 3. 软硬件划分依据与接口设计

## 3.1 划分原则

本作品的划分依据是**"什么是确定的、什么是易变的"**：

| 判据 | 放在硬件（RTL） | 放在软件（PC 端脚本） |

| **时序必须确定** | ✅ 音频采样、I2S 时序、显示扫描、SD 协议 | ❌ |
| **每次运行都一样** | ✅ FFT 蝶形、EQ 滤波、频谱分组 | ❌ |
| **需要人机交互调参** | ✅ 配置寄存器组（1 拍生效） | ❌ |

## 3.3 接口设计

### 3.3.1 板级接口

| 接口 | 方向 | 协议/电平 | 关键约束 |
|---|---|---|---|
| **WM8960** | 双向 | I2C（SCL/SDA）+ I2S（BCLK/LRCLK/ADCDAT/DACDAT）| WM8960 为 I2S 主，FPGA 为从 |
| **LCD** | 输出 | RGB888 + HS/VS/CLK，3.3 V | 时序：七项守恒（总拍数/有效像素/前后肩）|
| **HDMI** | 输出 | TMDS 4 对差分，LVCMOS33 + 51Ω 串阻 | **板上无发送芯片**，FPGA 直连 J5 |
| **SD 卡** | 双向 | SPI（CLK/MOSI/MISO/CS）| LVCMOS33，Bank 14 |
| **UART** | 双向 | 115200 8N1，CH340E | ASCII 命令通道 |
| **按键** | 输入 | 2 个板载 + 触摸屏（XPT2046 SPI）| 20 ms 消抖 + 300 ms 双击窗 |
| **QSPI Flash** | 双向 | W25Q128JVSQ，4 线 QSPI | 固化后掉电自启动 |

### 3.3.2 模块间的关键接口契约

**① 音频抽头（`audio_top` → `fft_core`）**

```verilog
output wire signed [23:0] spec_l, spec_r;   // Q1.23，均衡后 / 音量前
output wire               spec_valid;       // 每采样一拍
```

**拍点位置的选择**：取**均衡后、音量前**——显示的是"处理后的频谱"，
而不是原始频谱。这样 EQ 的调节效果在频谱上立即可见。

**② 频谱结果（`spectrum` → `disp_mix`）**

```verilog
output wire [59:0][8:0]  bars;          // LCD：60 根柱，9 位高
output wire [79:0][8:0]  bars80;        // HDMI：80 根柱
output wire              frame_done;    // 一帧算完的单拍脉冲
```

**③ 帧缓冲（`sd_img_load` → `frame_buf` ×2）**

```verilog
output wire [18:0] wr_addr;    // 第 1 份：线性地址 = y*480 + x
output wire [15:0] wr_data;    //         RGB565
output wire        wr2_en;     // 第 2 份：只在裁剪区内有效
output wire [18:0] wr2_addr;   //         = (y-46)*320 + (x-80)
```

**⚠️ 设计约束**：`wr_en` / `wr_addr` / `wr2_en` / `wr2_addr` 驱动 BRAM 的
`ENARDEN` / `ADDRARDADDR`，**绝不能带异步复位**（否则触发 `DRC REQP-1839`）。
它们由 `start` 清零 + 每拍给默认值。

# 4. 优化过程与性能资源对比

## 4.1 优化总览

本作品经历了 **5 个主要优化阶段**，每阶段的量化收益如下：

| 阶段 | 优化内容 | 关键指标变化 |
|---|---|---|
| **①** | **同步复位替代异步复位** | `DPOR-1`: 11 → **0**；WNS: +1.117 → **+2.156 ns**；LUT: 6802 → **5648** |
| **②** | **FFT 从全并行改单蝶形时分复用** | DSP: 2048 → **4**（1/512）；BRAM: 0 → 2 |
| **③** | **HDMI 大屏（80 根柱 + 波形）** | 新增功能；WNS 仍为正 |
| **④** | **SD 图片背景（双帧缓冲方案）** | BRAM: 68.5 → **100.5**（+32，而非 +84）|
| **⑤** | **综合警告清零** | 警告: 51 → **0** |

## 4.2 详细优化记录

### 优化 ①：同步复位替代异步复位

**问题现象**：

```
[DRC DPOR-1] × 11 条
[DRC REQP-1839] × 180 条
WNS = +1.117 ns（勉强收敛）
```

**根因分析**：
`eq_cascade` / `i2s_rx` / `i2s_tx` / `i2s_clkgen` / `audio_top` / `cdc_sync`
共 6 个文件用 `always @(posedge clk or negedge rst_n)`。而本工程的 `rst_n`
来自 `rst_sync`（**已经是域内同步释放**），所以异步复位在这里**一点好处都没有，
纯代价**：DSP48 的内部寄存器只有同步复位能力，带异步复位就无法被吸收进 DSP，
额外消耗约 1154 个 LUT 做置位/复位逻辑。

**修复**：全部改成 `always @(posedge clk)` + `if (!rst_n)`。
`rst_sync.v` 自己**保留**异步（它就是复位产生器）。

**量化收益**：

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| `DPOR-1` | 11 | **0** | ✅ |
| WNS | +1.117 ns | **+2.156 ns** | **+1.04 ns** |
| Slice LUTs | 6,802 | **5,648** | **−1,154** |

**⚠️ 教训**：**「已修复」要按根因全量重扫** —— 这个根因**第 4 次复发**，
前 3 次都是只改报出来的那一处。

### 优化 ②：FFT 从全并行改单蝶形时分复用

**问题**：1024 点 FFT 若全并行需 512 个蝶形 × 4 乘法器 = **2048 个 DSP48**，
而器件只有 **240 个**（超 8 倍）。

**方案对比**：

| 方案 | 蝶形单元 | DSP48 | BRAM | 整帧耗时 | 占帧周期 |
|---|---|---|---|---|---|
| 全并行 | 512 | 2048 | 0 | 1 拍 | 0.04% |
| 4 路并行 | 128 | 512 | 0 | 7,680 拍 | 0.3% |
| **单蝶形（采用）** | **1** | **4** | **2** | **30,720 拍** | **1.3%** |

**为什么单蝶形够用**：48 kHz / 1024 点 ⟹ 帧周期 **46.9 ms**；
整帧耗时 30,720 × 20.83 ns = **0.64 ms**，仅占 **1.3%**，
剩余 75 倍时间裕量。

**实现要点**：

- **in-place 运算**：蝶形的两个输入与两个输出用同一对地址，BRAM 只需 1024×24 bit ×2（实部/虚部）
- **地址发生器用"位操作"而非除法**：第 `stage` 级的两个点地址
  ```verilog
  p = ((cnt >> stage) << (stage+1)) | (cnt & lo_mask);   // 插 0
  q = p | (1 << stage);                                   // 插 1
  ```
- **旋转因子索引** `tw_idx = (cnt & lo_mask) << (LOG2N-1-stage)`

**资源实测**：**1004 LUT / 126 FF / 2 BRAM36 / 4 DSP48**，WNS +2.54 ns @ 48 MHz。

### 优化 ③：HDMI 大屏

**新增能力**：640×360@60，80 根独立柱 + 波形 + 程序化背景，无 UI。

**关键参数选择**：

| 分辨率 | 柱数 | 每柱像素 | 是否整除 |
|---|---|---|---|
| 640×360 | 60 | 10.67 | ❌ **不整除 ⟹ 需乘法** |
| **640×360** | **80** | **8** | ✅ **整除 ⟹ 可纯移位** |
| 480×272 | 60 | 8 | ✅ 整除 |

**⟹ 选柱数优先能整除屏宽的**。并且**数据柱数（60）与显示柱数（80）分离**，
用 `generate` 的恒等分支保证 LCD 路径零变化。

**踩坑**：`spectrum_map` 曾是按 60 根**硬编码**的 ROM，`default: last_bin = 0`
⟹ `NBARS=80` 时 `frame_done` 永不触发 ⟹ 柱谱全没。
**修法**：生成器做成参数化（`--nbars` / `--out` / `--module`）并生成 `spectrum_map80.v`。

### 优化 ④：SD 图片背景（双帧缓冲）

**这是一次"试了 4 个方案"的优化**，完整对比如下：

| 方案 | 存储 | 每份 BRAM | 份数 | 总 BRAM | 时序 | 结论 |
|---|---|---|---|---|---|---|
| **A** 640×360×16 | 3.69 Mb | 103 | 2 | 206 | ❌ | **超器件** |
| **B** 640×360×8（RGB332）| 1.84 Mb | 52 | 2 | 104+30=**134** | ⚠️ +0.011 ns | **能构建 ✗ 但 256 色色带太重（实测否定）** |
| **C** 320×180×16（LCD 居中）| 0.92 Mb | 26 | 1 | **36.5** | ✅ +1.84 ns | **省资源 ✗ 但 LCD 有黑边** |
| **D** 480×272×16 + 320×180×16 ⭐ | 2.09+0.92 Mb | 58+26 | 2 | **100.5** | ✅ **+1.78 ns** | **采用** |

**为什么不用"一个缓冲两个读口"**：

```
Vivado 的 BRAM 推断不支持"1 写 2 读（跨时钟）"
   ⟹ 退化成 LUTRAM ⟹ DRC UTLZ-1：需要 86,452 个 RAMD64E，只有 19,000 个
   ⟹ 加 (* ram_style = "block" *) 也无效（属性只是建议，访问模式才决定映射）
   ⟹ 必须复制实例
```

**最终方案的数据流**：

```
SD 字节流 ⟹ sd_img_load
              ├──► frame_buf_lcd  480×272（58 块）⟹ LCD 1:1 满屏
              └──► frame_buf_hdmi 320×180（26 块）⟹ HDMI 裁中心后 2× 放大
                    ↑ 只在 [80,400)×[46,226) 范围内写
```

**裁剪地址的计算（零 DSP）**：

```verilog
wire [15:0] crop_dy = y_cnt - CY;
wire [18:0] crop_addr = ({3'd0, crop_dy} << 8) + ({3'd0, crop_dy} << 6) + {3'd0, crop_dx};
//                      dy*256          +          dy*64            + dx
//                      = dy*320  ✓ 两次移位相加，不用乘法器
```

**2× 放大（零成本）**：

```verilog
assign fb_addr = ((fb_ly >> 1) * FB_SW_U) + (fb_lx >> 1) + 1;
//                    ↑ 右移 1 位 = 除以 2
```

## 5.4 自我纠错轨迹（典型 5 例）

### 例 1：`str.replace()` 静默成功

**现象**：改完 `top.v` 的 `disp_top` 实例参数，脚本输出 "OK"，但上板实测
LCD 仍居中显示图片、颜色不对、画面错位重叠。

**定位过程**：
```bash
# 回看修改脚本的输出 ⟹ "top OK"
# 直接 grep 文件 ⟹ 参数还是旧的！
$ grep -n "FB_SW(" rtl/top.v
876:    .FB_SW(320), .FB_SH(180), .FB_W(320), .FB_H(180),   ← 没改到
877:    .FB_X0(80), .FB_Y0(46), .SHIFT(0))
```

**根因**：`str.replace(old, new)` 在 `old` 不匹配时**静默返回原串**，
不报错、不警告。

**修复**：
```python
assert old in s, "搜索串没找到！"     # ⟹ 不匹配就崩，绝不静默
s = s.replace(old, new)
```

**沉淀为账本 807 条**：`str.replace()` 找不到就静默成功，是自动化改码最大陷阱。

---

### 例 2：BRAM 被推断成 LUTRAM

**现象**：合成报 `DRC UTLZ-1`：需要 86,452 个 `RAMD64E`，只有 19,000 个。

**定位过程**：
1. 直觉是"640×360×16 太大"⟹ 但算下来只要 103 块 BRAM（器件有 135 块）
2. 看报告：**"LUT as Distributed RAM"** 超限 ⟹ 说明根本没映射到 BRAM
3. 检查 `frame_buf.v`：`mem` 被**两个不同时钟**读（`rd_clk` 和 `rd2_clk`）
4. 加 `(* ram_style = "block" *)` ⟹ **重新合成，仍然 LUTRAM**
5. 查 UG473：BRAM 推断模板只支持 **1 写 + 1 读**（简单双口）或**真双口**（需原语）

**修复**：不用一个缓冲两个读口，改成**两份不同尺寸的缓冲实例**。

**沉淀为账本 789/790/792 条**。

---

### 例 3：`wr_en` 类信号误放进异步复位块

**现象**：综合报 **40 条 `REQP-1839`**（RAMB36 的异步控制脚检查）。

**定位过程**：
```bash
$ grep "REQP-1839" build.log | head -1
... has an input control pin .../ADDRARDADDR[0] (net: u_fb_hdmi/wr_addr[0])
    which is driven by a register (u_img_load/wr2_addr_reg[0])
    that has an active asynchronous set or reset.
```

**根因**：我给 `sd_img_load` 加第二个写口时，把 `wr2_en` / `wr2_addr`
放进了 `if (!rst_n)` 块。而**同一个文件里 `wr_addr` / `wr_en` 的注释
明确写着"不能带异步复位"** —— 我违反了这条。

**修复**：移出异步复位块，改由 `start` 清零 + 每拍给默认值。

**沉淀为账本 813 条**：加新信号时要先看"同族信号是怎么处理的"。

---

### 例 4：`y[8:3]` 在 360 行时回绕

**现象**：用户反馈"LCD 和 HDMI 的程序化背景不一致"。

**定位过程**：
1. `bg_src` 是**纯组合**函数 `(x,y,mode) → rgb`，同一个 (x,y) 必然同色
2. 但两个实例的 `VDISP` 不同：LCD 272 / HDMI 360
3. 检查渐变代码：`wire [5:0] t = y[8:3];`
4. **算一下**：272 行时 `y[8:3]` = 0..33 ✓；360 行时 y ≥ 256 ⟹ `y[8:3]` **回绕到 0**
   ⟹ 下半屏渐变从头开始 ⟹ 观感完全不同

**修复**：
```verilog
localparam integer YSH = (VDISP >= 512) ? 4 : 3;
wire [5:0] t = y[YSH +: 6];      // 272 行取 3（与原来一致），360 行取 4
```

**沉淀为账本 811 条**：用绝对坐标做图案，换分辨率必然错。

---

### 例 5：颜色不对 —— 数清"反转层次"

**现象**：HDMI 输出图片，原图深蓝却显示成**暖黄**；LCD 正常。

**定位过程**：
1. "深蓝 → 暖黄"是 **R/B 互换的教科书特征**（互补色同时出现）
2. 数据链只有一处可能：`disp_top` 的 RGB565 → RGB888 展开
   ```verilog
   wire [23:0] fb_rgb888 = {fb_rgb[4:0],  ..., fb_rgb[15:11], ...};
   //                        ↑ 高字节 ← B          ↑ 低字节 ← R      ⟹ R/B 反了
   ```
3. 但这行是按**LCD 实测**写的（账本 545 条），且 LCD 显示正确
4. 推理：**LCD 面板接线本身是 BGR** ⟹ 这里"反"一次，面板又"反"一次 ⟹ 抵消
5. **HDMI 走标准 RGB ⟹ 没有第二次反 ⟹ 必须在这里换回来**

**修复**：
```verilog
.pix_rgb({hdmi_rgb[7:0], hdmi_rgb[15:8], hdmi_rgb[23:16]})   // 仅 HDMI 路径
```

**沉淀为账本 810 条**：一路对一路错的颜色问题，先数清反转层次
（面板 BGR + 数据 RGB + 标准 RGB 三层叠加）。

### 5.5.2 关键工作流规则（从失败中总结）

| 规则 | 来源 |
|---|---|
| **不在红树上继续改** | 一次改坏后连改 3 次都不中 ⟹ 改成 `git checkout -- <files>` 回退，重新开始 |
| **大改动先建分支** | 在 `master` 上改到一半 TB 红 ⟹ 只能全量回退；建 `fb320` 分支后，WIP 可安全提交 |
| **每轮必须跑全量回归** | 曾因"只跑相关 TB"漏掉 `tp_edges` 的 UNDRIVEN |
| **加速先看 `user`/`real` 比值** | `run_iv.sh` 从 20m54s → 1m30s：瓶颈不是并行度，是单个 `tb_top` 吃 20 分钟 |
| **GUI 能做的事 = 一串 Tcl** | Flash 烧写 CLI 失败 7 轮 ⟹ 照抄 GUI 的 Tcl Console ⟹ 一次成功 |
| **同一问题连猜 3 次不中 ⟹ 停止猜测** | HDMI 撕裂问题猜了 4 次（复位延迟 256 周期 / 2.6 ms / locked AND / OSERDESE2）⟹ 改用文档记录 + 待 ILA |
| **失败尝试要写进文档标"已试过 ✗ 无效"** | 避免重复走死路 |
| **`str.replace` 必须 `assert`** | 见 5.4 例 1 |
| **批量改注释比改代码更危险** | 注释缺一个 `//` 就把代码改坏，且 iverilog 可能只报一行 |

| A-01 | 采纳 | 无 | ✅ 与 Python 黄金模型逐位一致 |

| A-03 | 采纳 | 无 | ✅ 2048 频点逐位一致 |
| A-04 | 部分采纳 | 格雷码 FIFO 改为"电平翻转 + 双打 + 边沿检测"（start 是单拍脉冲，会被漏掉）| ✅ 4/4 PASS |
| A-05 | 部分采纳 | 加 `WITH_UI`/`WITH_TEXT`/`FB_*` 参数族 | ✅ 130560 像素逐点一致 |
| B-01 | 采纳 | 多次人工纠错（见 5.4）| ✅ 41/41 |
| B-02 | 采纳 | 无 | ✅ 逐位一致 |
| B-03 | 采纳 | `gen_spectrum_map.py` 后来参数化 | ✅ 60/80 两种柱数都验证 |
| B-04 | 部分采纳 | Flash 烧写改成"先 program_hw_devices 建 SPI 通道" | ✅ 43 秒成功 |
| B-05 | 采纳 | 无 | ✅ WNS 全为正 |
| B-06 | 采纳 | 全部人工核对数字 | ✅ 与 post_route 报告一致 |

**核验方法论**：

1. **逐位对拍**：RTL 输出 vs Python 定点模型，**不允许"看起来差不多"**
2. **独立真值**：用 `numpy.fft` / `$atan2` / `$sqrt` 当第三方真值，不用同一套公式自证
3. **穷举**：512 个 bin 分组、5132 组地址发生器、49920 个极坐标像素
4. **总量守恒**：液晶时序用"一帧 150150 拍、130560 个有效像素"来卡
5. **读回验证**：帧缓冲 130560 像素逐点写入再读回

## 6.3 从"观察"到"技能"的抽象过程

**以 `rtl-verification` 为例**，完整链路：

```
原始观察（账本 412 条）
  TB 里 `@(negedge sd_clk)` 采样，结果总差一拍
        │
        ▼ 追问"为什么"
根因
  `sd_clk` 是 `div_clk` 分频来的 ⟹ `negedge sd_clk` 恰好等于 `posedge div_clk`
  ⟹ 在"上升沿那一刻"读到的是【旧值】
        │
        ▼ 再问"这是个例还是通类"
聚类（账本 413/414/415 条）
  · `wire rx_next = {rx[46:0], din};` —— 非阻塞赋值在同一 always 读不到新值
  · `acmd41_cnt` 在 CS 沿被清零 —— 跨帧状态和帧内状态不能共用一个复位
  · 边际推理调不动 —— 换成显式计数 `edge_n`
        │
        ▼ 抽象成规则
技能包条目
  "**永远不要在信号自己更新的沿上读它**"
  "**非阻塞赋值：同一 always 里读到的是上一拍的值**"
  "**复位的作用域要精确界定：跨帧状态 ≠ 帧内状态**"
        │
        ▼ 写成"判据"
可执行检查
  写 TB 时自问：这个 `@(posedge/negedge X)` 和 X 的驱动沿是同一个吗？
  如果是 ⟹ 改成 `@(posedge clk); #1;` 或换一个沿
```

## 6.4 技能包如何验证有效

| 验证方式 | 具体做法 |
|---|---|
| **重做旧任务** | 用 `fixed-point-dsp` 的流程重做 EQ ⟹ 频响误差 3 dB → 0.5 dB |
| **看新任务是否不再犯** | `WAVE_AMP` 截断问题后，新加的 6 个位宽参数**零次复发** |
| **看效率指标** | 构建时间、回归时间、单次"改-验"循环时长 |
| **看"是否被自己引用"** | 后续 20 次改动中，有 14 次在改之前先读技能包对应章节 |

## 6.5 边界的确定方法

**判据：技能包里的每一条都必须能回答三个问题**

1. **它解决什么现象？**（否则无从触发）
2. **它的前提是什么？**（否则用错场景）
3. **前提不成立时会怎样？**（否则变成教条）

**示例（`fpga-rtl-flow` 中"BRAM 推断"条）**：

| 问题 | 答案 |
|---|---|
| 解决什么现象 | 综合报 `DRC UTLZ-1`，LUTRAM 超限 |
| 前提是什么 | 存储器要映射到 BRAM，且访问模式符合推断模板 |
| 前提不成立 | 若用 `(* ram_style = "distributed" *)` 故意要 LUTRAM（小表、多端口），本条不适用 |

**⚠️ 写进技能包的反面例子**（**避免把特例当通例**）：

```
❌ 不要写："BRAM 一定要加 (* ram_style = "block" *)"
   —— 实测这条属性在"1 写 2 读跨时钟"下【无效】

✅ 应该写："BRAM 推断由【访问模式】决定，属性只是建议。
           1W1R ⟹ 可靠；1W2R 跨时钟 ⟹ 退化成 LUTRAM，属性也救不了。"
```

## 7.4 常见问题

| 现象 | 原因 | 解决 |
|---|---|---|
| **`run_iv.sh` 全部失败** | iverilog 版本太老 | 需要 ≥ 11.0（支持 `-g2005` 的部分特性）|
| **仿真通过、综合报 `UTLZ-1`（LUTRAM 超限）** | 存储器的多端口访问模式不匹配推断模板 | 复制实例，不要加读口（见 5.4 例 2）|
| **`place_design` 失败但没报时序** | BRAM 占用 > 95% ⟹ 布线拥塞 | 看 `post_route_util.rpt`；降位深/降分辨率 |
| **上板后 LCD 全白/全黑** | LCD 时序参数错 | 跑 `bash scripts/sim/run_iv.sh lcd_timing` |
| **SD 图片显示乱码/斜切** | 卡里的数据尺寸与 RTL 的 `W/H` 不匹配 | 重新用 `mkimage.py` 写卡；确认每图 261120 字节 |
| **HDMI 颜色不对（暖黄）** | R/B 通道互换 | 见 5.4 例 5 |
| **HDMI 复位后偶尔右半屏撕裂** | **已知未解决问题**（TMDS 层）| 重按复位通常可恢复；需 ILA 或示波器深入 |
| **线路输入无声** | 板上 `C4`(1µF) 开路 | 需补焊（硬件问题，代码已就绪）|
