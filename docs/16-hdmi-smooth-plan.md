# HDMI 2 倍放大的平滑方案（待实施）

> 当前状态：`SMOOTH` 参数已设计好但**未实现**。上一次尝试写歪了（`sm_out`
> 未使用、`sm_de/hs/vs` 没驱动、算术错误），已回退。下面是正确做法。

---

## 1. 为什么需要

```
HDMI 侧：320×180 存储 ⟹ 2 倍放大到 640×360
       ⟹ 每个源像素变成 2×2 的方块 ⟹ 明显像素化（用户实测反馈）
```

## 2. 水平 2× 平滑（成本最低，效果明显）

```
源像素序列：sx = lx >> 1  ⟹ 0,0,1,1,2,2,3,3,...

偶数列 lx[0]=0  ⟹ 输出 p(sx)
奇数列 lx[0]=1  ⟹ 输出 (p(sx) + p(sx+1)) / 2

关键：sx 每拍只增 0 或 1
   ⟹ 只需缓存"上一拍读到的样本" + "本拍读到的样本"
   ⟹ 1 个寄存器，不需要行缓冲 ✓
```

**⚠️ 代价：输出延迟 1 拍 ⟹ 所有同步信号必须一起延迟**

## 3. 正确的实现骨架

```verilog
localparam integer DO_SMOOTH = (SMOOTH != 0) && (SHIFT == 1);

// 读地址提前 2 个像素（而不是现在的 1 个）⟹ 抵消多出来的一拍延迟
assign fb_addr = fb_sy * FB_SW_U + fb_sx + 19'd2;

reg [23:0] p_cur;    // 本拍到达的像素（对应 fb_lx）
reg  [0:0] lx_d1;    // 延迟 1 拍的 lx[0]
reg        in_d1;    // 延迟 1 拍的 fb_pix_now
// ★ 同步信号也必须延迟 1 拍（或者用"读地址提前 2"来抵消 —— 二选一！）

always @(posedge clk_pix) begin
    p_cur <= fb_rgb888;
    lx_d1 <= fb_lx[0];
    in_d1 <= fb_pix_now;
end

// 每通道：p_cur 与"上一拍的 p_cur"取平均（用寄存器延迟链）
reg [23:0] p_prev;
always @(posedge clk_pix) p_prev <= p_cur;

wire [23:0] avg = { (p_prev[23:17] + p_cur[23:17]) >> 1, 3'b000,
                    (p_prev[15:9]  + p_cur[15:9])  >> 1, 2'b00,
                    (p_prev[7:1]   + p_cur[7:1])   >> 1, 1'b0 };

wire [23:0] fb_rgb_smooth = DO_SMOOTH ? (lx_d1 ? avg : p_cur) : p_cur;
```

**❗最关键的坑：`de` / `hs` / `vs` 也必须延迟，且延迟量要和数据完全一致。
否则画面整体右移 1 像素（`de` 比数据早一拍）。**

**⭐ 推荐做法：不要延迟同步信号，而是把【读地址提前 2 个像素】**
（现在是 `+1`，改成 `+2`）⟹ 数据晚 1 拍到达，但位置仍然对齐 ✓

## 4. 验证办法

1. `tb_disp_top` 必须保持绿（`SMOOTH=0` 时行为完全不变 ⟹ 应该直接绿）
2. 新增判据：`SMOOTH=1` 时，**同一行内相邻输出像素在源边界处不应出现"突跳"**
3. 上板看：方块边界是否变柔和

## 5. 风险与代价

| 项 | 值 |
|---|---|
| LUT | +约 60（24 位 × 2 寄存器 + 3 个 8 位加法器）|
| BRAM | 0 |
| 时序 | **保持路径变长 1 级加法** ⟹ `clk_hdmi` 有 +4.0 ns 余量，够 |
| 风险 | **同步信号对齐 ✗ 错了会整体偏移 1 像素** |

## 6. 可选：垂直也平滑

需要**一行行缓冲**（320 × 16 bit = 640 字节 ⟹ 1 块 BRAM）：
```
偶数 ly ⟹ 用本行
奇数 ly ⟹ 用 (本行 + 上一行) / 2
```
成本：1 块 BRAM + 1 套行指针逻辑 ⟹ **复杂度约是水平方案的 3 倍**。
**建议先做水平版，看效果再决定要不要垂直。**
