# 08 开发经验沉淀：Skills 索引

> 本项目把开发过程中**踩过的坑、定下的流程、验证的方法**封装成了 3 个可复用 Skills，
> 放在 `.pi/skills/` 下。它们既是**工程资产**（换项目能直接复用），
> 也是**过程证据**（记录了每个问题从现象到根因到修复的完整链条）。

---

## 1. 什么是 Skill

Skill 是**按需加载的能力包**：平时只把「名字 + 一句话描述」放进上下文，
当任务匹配时才把完整内容读进来（progressive disclosure），
避免无关信息占用上下文。

结构：

```
.pi/skills/<skill-name>/
├── SKILL.md              # 必需：frontmatter（name + description）+ 主流程
└── references/           # 可选：深入文档，主文件里用相对路径链接
    └── xxx.md
```

调用方式：
- **自动触发**：描述里写清了"什么时候用"，任务匹配时自动加载
- **手动触发**：`/skill:fpga-rtl-flow`

## 2. 三个 Skills

| Skill | 一句话职责 | 何时触发 |
| --- | --- | --- |
| **`fpga-rtl-flow`** | 纯 RTL 工程的无 GUI 开发流程 | 要仿真/综合/构建 FPGA 工程、写 Tcl 流程、排查构建报错 |
| **`fixed-point-dsp`** | 定点 DSP 的位宽预算与结构选择 | 实现滤波器/FFT、选 Q 格式、评估定点精度、排查"频响不对" |
| **`rtl-verification`** | 与 Python 定点黄金模型逐位对拍 | 建自动化验证、写 testbench、排查"仿真不通过/差一拍" |

### `fpga-rtl-flow`（核心流程）

- **两条腿走路**：iverilog 秒级验功能，Vivado 分钟级验能否上板
  （附真实反例：组合环在 iverilog 里恰好收敛，三条 testbench 全过，Vivado DRC 才抓到）
- 非工程模式 vs 工程模式、GUI 工程共存的 4 个坑
- 报告解读：资源/时序/DRC 各看什么、危险信号是什么
- 约束要点：过约束反推 Fmax、CFGBVS/CONFIG_VOLTAGE

`references/`：
- `mmcm-clocking.md` —— MMCM 可达频率计算（**含 `CLKOUT0_DIVIDE_F` 1/8 步进这个关键点**）、
  穷举脚本、一个 MMCM 不能产出两个不相关频率的证明、`locked` 同步写法
- `vivado-batch-cheatsheet.md` —— 完整 Tcl 命令、报告解读、7 类常见报错

### `fixed-point-dsp`（精度预算）

- **位宽 ≠ 小数位**：`signed [17:0]` 配 `2^-17` 的范围是 `[−1,1)`（Q0.17），配 `2^-16` 才是 `[−2,2)`
- **DSP48E1 25×18 的操作数分配**：三种方案与取舍
- **舍入/饱和**：`>>>` 与 Python `>>` 的 floor 语义一致；累加器隐式截断必须在模型里显式模拟
- **条件数优先于位宽**：定点误差比预期大一个数量级时，**先换结构再加位宽**

`references/`：
- `q-format-and-rounding.md` —— 标度推导、位级对齐检查表、负数 hex 向量写法
- `biquad-structure-choice.md` —— 相消的定量分析、一阶 vs 二阶的实测对比、频响评估的 `a0` 陷阱

### `rtl-verification`（验证方法）

- **黄金模型必须是定点的**，判据是**逐位相等**（`!==`），不是"误差小于阈值"
- **三段式激励**：冲激 / 多音 / 满量程方波（专门覆盖饱和分支）
- **协议行为模型**：写一个"另一个芯片"，双向独立判定（避免收发同错互相抵消）
- **系统级用冲激响应比对**：自动定位 IR 起点，不需要预知流水线延迟，顺便拿到端到端延迟实测值

`references/`：
- `golden-model-method.md` —— RTL ↔ Python 位级映射表、代码组织、ROM 生成策略、常见反模式
- `debug-playbook.md` —— **按现象分类的排查决策树**（输出全零 / 数量不对 / 差一拍 / 数值偏差 / 完全对不上 / 编译失败）

## 3. 方法论：问题 → 定位 → 修复 → 沉淀

每个坑都走完这条链才写进 Skill：

```
① 现象     可观测的异常（数值差多少、哪一路错、什么条件下出现）
② 定位     用对比/二分/dump 把范围缩小到具体一行（不是猜）
③ 修复     最小改动，改完立刻重跑验证
④ 量化     修复前后各测一次，拿到可比数字
⑤ 沉淀     抽象成规则，写进 Skill 的"踩坑"章节
```

**没有第 ④ 步的经验不是经验，是感想。** 下面这张表就是所有第 ④ 步的产出。

## 4. 问题账本（过程证据）

> 共 56 条。每条都走完「现象 → 根因 → 修复 → **量化改善**」四步。
>
> 第 17~20 条是同一轮里用**四种不同的手段**发现的，对照着看很有价值：
> **17 靠综合器报错、18 靠 DRC、19 靠资源报告、20 靠时序报告。**
> 四个 bug 里只有 0 个能被仿真发现。
>
> 第 21~22 条是同一类问题的两面：**手算容易错的换算/位域，就该交给脚本生成**。
> 第 23 条比较特别 —— **是 testbench 自己写错**，说明验证代码同样需要
> 被怀疑：报错的时候要先确认是 DUT 错还是 TB 错。
>
> 第 24~26 条都发生在显示链，共同主题是**“看起来对，其实没在检查”**：
> 24 是声明位置导致编译直接失败（还算好的），
> 25 是 TB 对齐错导致满屏假错误，26 最阴 —— 工具报告干净，
> 实际是**根本没分析**；29 是反面 —— 工具报了违例，但**它本来就不该算那条路径**。
>
> 第 18/19/30/45 条是**同一根因的四次出现**：异步复位。
> 它分别表现为 DRC 违例、资源浪费、DSP 无法合并寄存器、
> 以及**又一次 DRC 违例** —— 而且第 4 次是在「以为已经全清掉了」之后。
> 教训升级：**改完要全量重扫，不能只改被报出来的那一处。**
>
> 第 46 条更阴：复位【风格】改对了，但复位【连接的位置】不对 ——
> 它被综合器顺手接到了 BRAM 的控制脚上，照样触发同一条 DRC。
> 「同一个 DRC 换了个人来犯」比「同一个模块犯两次」难查得多。
>
> 第 49/50 条是**上板才暴露**的一对：49 是 DUT 的真 bug（命令写一半时
 `?` 被吞、状态机卡死），50 是**测试工具自己在说谎** —— 把失败藏进了
 `if` 里不计入统计。**49 能活下来，正是因为 50**。
 TB 也测不到 49：它测非法字符时状态机一直停在 `S_CMD`，
 而 `S_CMD` 本来就有"其它字符一律忽略"。**要测中间态，就得先制造中间态。**

 第 52 条最特别：**iverilog 和 Verible 都放过了它** —— 连 `-Wall` 都不报，
 TB 也全过，**只有综合器抓到了**。这直接暴露了一个流程漏洞：
 回归全绿不等于设计合法。见第 52 条。

 第 47 条是关于**「零警告」这个目标本身**的：
> 不是所有警告都该被消掉。有些警告的前提在你这个设计里根本不成立，
> 硬消它反而会让设计变差。判据要写下来，而不是默默 waive 掉。
>
> 第 23/25/28/32 条是**同一个陷阱的第 1~4 次**：拿一个和被观测信号
> 不同拍的信号去比对（非阻塞赋值、寄存输出、同步器延迟都会造成）。
> 写 TB 时先搞清楚「这个信号在哪一拍稳定」，再决定在哪一拍采样。
>
> 第 34 条是另一种教训：**近似公式的误差指标不能凭印象写**。
> 「±4.3%」我写过很多次、也被人引用过，直到真的穷举比对才发现是 +9.1%。
> 凡是写进文档的数字，要么有出处，要么自己算一遍。
>
> 第 37/38 条是**参数化改造的连带代价**：柱数 30→60 看起来只是改一个常量，
> 实际上牵动了 **位宽**（5→6 位）、**几何**（16→8 px）、**扇区数**（32→64）、
> **TB 里的镜像常量**（圆心、扫描范围）。
> 教训：改一个「全局参数」之前，先列出所有依赖它的地方 —— 这本身就是需求。
>
> 第 39 条是**语法习惯差异**：C 语言里 `for` 后跟缩进的多行语句是合法的，
> 所以很容易习惯性省略花括号；Verilog 不行。
> **多行循环体一律加 `begin/end`，哪怕只有一句也加上。**

## 6. Skill 编写规范速查

| 项 | 要求 |
| --- | --- |
| 目录 | `<skill-name>/SKILL.md`，`references/` 放深入文档 |
| `name` | ≤64 字符，仅小写字母/数字/连字符，无首尾连字符、无连续连字符 |
| `description` | ≤1024 字符，**必须写清"什么时候用"**（这决定它会不会被自动加载） |
| 相对链接 | 主文件里链接 `references/xxx.md`，路径相对 skill 目录 |
| 内容组织 | 核心原则 → 流程（命令级）→ 决策表 → 踩坑清单 → 验收标准 |
| 反例 | **不要写成日志**。要有判断规则和"什么时候不适用" |

**description 的好坏直接决定技能会不会被用上：**

```yaml
# ✗ 差：不知道什么时候该用
description: 帮助处理 FPGA。

# ✓ 好：说清了能力和触发场景
description: 纯 RTL FPGA 工程的无 GUI 开发流程。覆盖工具链定位与自检、
  iverilog 秒级快速仿真、Vivado batch 模式综合/实现/比特流、构建报告挖掘、
  GUI 工程与非工程模式共存、波形查看、MMCM 时钟规划。当需要仿真、综合、
  构建或上板一个纯 RTL FPGA 工程，或排查 "command not found"、组合环 DRC、
  时序违例、比特流无法生成等构建问题时使用。
```
